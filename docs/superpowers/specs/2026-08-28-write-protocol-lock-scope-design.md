# Write Protocol Lock Scope Redesign

Status: design, 2026-08-28. Target branch: `rewrite/single-context-impl` (evaluated at 18eb3289). All `file:line` citations below refer to that commit unless prefixed with `master:`.

## Problem

Two deadlocks were reproduced against the branch, both regressions versus master:

- **Repro A** (`src/Namotion.Interceptor.Tracking.Tests/GateChainDeadlockRepro.cs`): two contexts, each with a third-party `IWriteInterceptor` that performs a structural write into the other context after `next()`. Deadlocks on the branch (both threads park holding their own context's topology gate, each wanting the other's), passes on master.
- **Repro B** (`src/Namotion.Interceptor.Tracking.Tests/MonitorAbbaRepro.cs`): one lifecycle-free context, two subjects, an interceptor cross-writing between them after `next()`. Deadlocks on the branch (unordered ABBA on the two per-subject attachment monitors), passes on master.

Both were reproduced in this worktree before any change (40 s timeouts), and both pass under the prototype described in "Prototype evidence" below (about 50 ms).

## 1. Verdict on the diagnosis

**Partially right.** The diagnosis has two claims; one is confirmed, one is refuted.

**Confirmed: the executor's lock scope is wider than any guarantee requires.** `InterceptorExecutor.SetStructuralPropertyValue` enters the lifecycle gate at `src/Namotion.Interceptor/Interceptors/InterceptorExecutor.cs:275`, the attachment monitor at `InterceptorExecutor.cs:278`, and then runs the entire interceptor chain inside both (`InterceptorExecutor.cs:285` calling `WriteStructuralValue`, which executes the chain at `InterceptorExecutor.cs:329`). The lifecycle-free arm holds the monitor alone across the chain (`InterceptorExecutor.cs:265-271`). That scope covers third-party interceptor code, property-change subscriber dispatch, and derived cascades on the unwind, none of which the ordering guarantee needs. It is also confirmed that pinning does not require the locks: the pinned-state property from `c78328af` is a single volatile read threaded from the routing decision into the chain resolution (`PinState` and the `FromState` overloads, `src/Namotion.Interceptor/InterceptorSubjectContext.cs:193-196` and `:239` in the commit's diff), and nothing about that read depends on any monitor being held. The conflation is real.

**Refuted: fixing the executor alone does not fix Repro A, so this is not only an executor lock-scope error.** `LifecycleInterceptor.WriteProperty` takes the gate itself inside the chain and holds it across `next()` (`src/Namotion.Interceptor.Tracking/Lifecycle/LifecycleInterceptor.cs:128-155`, `next` at `:141`). Every first-party write interceptor orders before the lifecycle (`PropertyValueEqualityCheckHandler.cs:10` `[RunsFirst]`, `DerivedPropertyChangeHandler.cs:20,25`, `PropertyChangeInterceptor.cs:22-23`, `SubjectTransactionInterceptor.cs:13`, `ValidationInterceptor.cs:14`), but a third-party interceptor registered without ordering attributes keeps insertion order (`InterceptorSubjectContext.cs:346-350` comment on `ComputeServices`) and therefore lands **after** the lifecycle, inside the gate held across `next()`. `OwnershipGraph.cs:494-497` documents exactly that placement. Repro A's interceptors are registered after `WithFullPropertyTracking`, so removing only the executor's outer hold still leaves their post-`next` cross-write running under the gate, and the deadlock stands. The design below therefore changes both the executor scope and the chain position of the lifecycle.

**Also confirmed as the real constraint the wide scope was papering over:** the monitor-across-chain is what today prevents a detach-and-reattach-elsewhere from interleaving with an in-flight commit. If the subject leaves context C and joins context D mid-chain, C's stale chain can commit a backing value that D's attach seeding already read past, leaving an untracked edge in D. Master had this window and admitted it (the reread comment in `master:src/Namotion.Interceptor.Tracking/Lifecycle/LifecycleInterceptor.cs`, in `WriteProperty`: "context.NewValue may differ from the backing store if another thread overwrote the property between our next() call and lock acquisition"). Any narrowing of the scope must replace that protection with something that closes the window rather than reopening it. That replacement is the terminal-time attachment check described next.

## The third shape

Master was deadlock-free but racy (validate after write, reread to converge). The branch is race-free but deadlock-prone (locks span user code). The third shape separates the two jobs the wide locks were doing:

1. **Topology atomicity** (claim before write, reconcile after write, no topology change interleaving with either) stays with the lifecycle gate, which the lifecycle already takes inside the chain. What changes is that no foreign code can run inside it, because the lifecycle becomes the last interceptor in every write chain, so `next()` under the gate is the terminal and nothing else.
2. **Commit-versus-transition atomicity** (a write commits only while the subject is attached to the context whose chain is executing) moves from "hold the monitor across the chain" to "check the attachment under the monitor at the terminal, immediately around the commit, and retry the whole write when it moved". The monitor is held for the commit only, never across user code.

A structural write that finds the attachment moved is re-routed from scratch against the fresh attachment. That is the same "orders rather than fails" semantics the current retry loop already documents (`docs/design/tracking-lifecycle.md`, "The Write Protocol": "every retry is caused by another thread completing an attachment transition"), moved from before the chain to around it.

### Why this closes master's reread race instead of reintroducing it

With the lifecycle last, the terminal commit of every attached structural write executes inside the lifecycle's gate section (`next()` at `LifecycleInterceptor.cs:141` reaches the terminal directly). Two concurrent writes to the same structural property therefore serialize their entire [claim, commit, reread, reconcile] sections on the gate. The reread at `LifecycleInterceptor.cs:145-146` can no longer observe another thread's commit that landed between this write's commit and its reconcile, because no other commit can land inside the gate section. The reread's remaining job is the one it legitimately has: observing what a normalizing setter actually stored, which is same-thread and deterministic. Master's shape could not do this because its lock began only after `next()` returned; the branch's shape did it by spanning the whole chain; the third shape does it by making the gate section contain the terminal but nothing user-registered.

## 2. The precise new lock scope, per route

Route classification stays as today: `TProperty` that can contain subjects routes structural (`InterceptorExecutor.cs:213`), everything else routes scalar; unattached means the lock-free attachment read returned null.

### Route 1: attached, context has a lifecycle (structural)

Executor (`SetStructuralPropertyValue`): **holds nothing**. Loop:

1. Volatile-read the attached context, pin its `ContextState` with one volatile read, resolve the chain from that pinned state (the existing `ExecuteInterceptedWrite(ContextState, ...)` overload, `InterceptorSubjectContext.cs:239`). No gate entry, no monitor entry, no lifecycle resolution in the executor at all; the routing decision and the chain are now the same artifact.
2. Mark the write context structural and record the expected context (two internal fields on `PropertyWriteContext<TProperty>`, which already carries per-call chain state such as `Terminal` and `Revision`, `src/Namotion.Interceptor/Interceptors/IWriteInterceptor.cs:47,62`).
3. Execute the chain.
4. If the chain flagged `AttachmentMoved`, go to 1 with a fresh routing read; otherwise return `IsWritten`.

Lifecycle (`WriteProperty`, now guaranteed last before the terminal): scalar, derived and non-intercepted properties pass through unchanged (`LifecycleInterceptor.cs:108-115`). Otherwise:

1. Lock-free precheck: if `subject.Executor.AttachedContext` is not this context, set `AttachmentMoved` and return without calling `next` (this replaces the current unvalidated write-through at `LifecycleInterceptor.cs:120-126`, which under the single-context model can only mean stale routing, because a chain only ever executes for the context the subject was attached to at routing time).
2. Enter the gate (`lock (_gate)`, as today at `LifecycleInterceptor.cs:128`). Re-check the attachment under the gate; if moved, set `AttachmentMoved` and return. Under the gate the attachment is frozen for all lifecycle-mediated transitions, because claims and releases require the gate (`OwnershipGraph.cs:21-24`, and both `AttachSubjectToContext` and `DetachSubjectFromContext` hold it, `LifecycleInterceptor.cs:271,304`). Transitions made through the raw SPI (`IInterceptorExecutor.TryUpdateAttachment` called directly) are caught by the terminal check below.
3. Under the gate, exactly as today: `IsOwned` check, `ClaimProposedComponent` (validate and claim the proposed component before the backing write, `LifecycleInterceptor.cs:136-139`), `next()` (now terminal-only), reread the authoritative getter, `Reconcile`, and `ReleaseUnusedClaims` in the `finally` (`LifecycleInterceptor.cs:141-154`).

Terminal (structural flavor, selected at chain compile time, see "Terminal flavors" below): `Monitor.Enter(attachment monitor)`; if `AttachedContext != expected context`, set `AttachmentMoved`, exit the monitor, and return without committing; else `lock (SyncRoot)` and commit exactly as today (backing write, `IsWritten`, revision increment, origin finalize, `SetWriteState`; `src/Namotion.Interceptor/Cache/WriteInterceptorFactory.cs:19-41`); exit the monitor.

Held while user code runs on this route: **nothing** for third-party interceptors, subscriber dispatch and derived cascades (all upstream of the lifecycle, so their post-`next` segments run after the gate is released). The gate covers, as today and as on master, the reconcile's user-code surfaces: lifecycle callbacks and events (contractually constrained, `LifecycleInterceptor.cs:48-49,60`, `CallbackReentrancyGuard.cs:59-63`), user collection and dictionary code enumerated by the scanner (master enumerated inside its lock too, `master:LifecycleInterceptor.cs` `FindSubjectsInProperty` under `lock (_attachedSubjects)`), read interceptors during the authoritative reread (also inside master's lock), and the terminal `writeValue` delegate (a registry dynamic property's stored setter can be user code, `src/Namotion.Interceptor.Registry/Abstractions/RegisteredSubjectProperty.cs:204`; on master that ran before the lifecycle's lock, on the branch it already runs inside gate and monitor, so this design does not widen it; it is listed as a residual in section 8).

### Route 2: attached, lifecycle-free context (structural)

Executor: same loop as route 1, holds nothing. Chain: the context's compiled chain, which contains no lifecycle. Terminal: the same structural flavor, so the commit is `monitor { check expected context; SyncRoot { commit } }`, and a moved attachment retries. There is no gate on this route because there is no topology to keep consistent: a lifecycle-free attach is root-only publication with no component walk and no seeding (`src/Namotion.Interceptor/InterceptorSubjectExtensions.cs:87-98,133-155`).

What the old monitor-across-chain bought here is fully replaced by the terminal check: if the subject is detached and attached to a lifecycle context D mid-chain, the commit either lands before D's claim (D's claim takes the same monitor via `TryUpdateAttachment`, `InterceptorExecutor.cs:113-134`, so its acquisition orders after the commit and D's seeding reads the committed value) or the check fails and the write re-routes through D's full protocol. Held while user code runs: **nothing**. This is what fixes Repro B.

### Route 3: unattached (structural or scalar)

The unattached arm stops bypassing the terminal. Today it writes the backing field directly under the monitor with no `SyncRoot`, no revision increment and no `SetWriteState` (`InterceptorExecutor.cs:313-321`); the design routes it through the zero-interceptor chain instead (`UninterceptedChain<TProperty>`, `InterceptorExecutor.cs:180-184`), whose terminal is given the **always-checking** flavor with expected context null: `monitor { check AttachedContext == null; SyncRoot { commit + revision + SetWriteState } }`, retry on failure. The always-checking flavor applies to the unattached route regardless of `TProperty` (see finding 3 in section 5 for why scalar-typed unattached writes need the check too).

Held while user code runs: nothing except the `writeValue` delegate under monitor and SyncRoot, which is the branch status quo minus the pre-chain hold.

### Route 4: scalar (attached)

Unchanged: no gate, no monitor, chain executed from a fresh state read, plain terminal (`InterceptorExecutor.cs:218-231`, `WriteInterceptorFactory.cs:19-41`). Two additions that cost one predictable branch each:

- The executor's scalar branch loops on `AttachmentMoved` exactly like the structural branch, because a narrowed structural write (structural declared type, scalar `TProperty`) reaches the lifecycle inside the chain (the lifecycle classifies on the declared type, `LifecycleInterceptor.cs:108`) and can now be flagged stale by step 1 or 2 of route 1. Today that staleness writes through unvalidated; the loop turns it into ordering.
- Retries must not lose the write origin: the `PropertyWriteContext` constructor consumes the thread-static pending origin stamp (`IWriteInterceptor.cs:121-130`), so the retry path re-uses the `AttemptedOrigin` captured by the first construction instead of consuming again (thread it through an internal constructor or hoist consumption out of the loop). This applies to all four routes.

### Terminal flavors

The terminal delegate is selected once per compiled chain, not branched per write:

- Attached chains are compiled per context and per `TProperty` (`InterceptorSubjectContext.cs:288-294`); when `PropertyTypeIndex<TProperty>.CanContainSubjects` is true the factory emits the checking terminal with the owning context captured as the expected context, otherwise the plain terminal. Scalar writes therefore pay zero new cost.
- The unattached zero-interceptor chain gets the checking terminal with expected null, for every `TProperty`.

The checking terminal needs the executor's monitor, reachable via `context.Executor` (already threaded, `IWriteInterceptor.cs:56`); expose the monitor internally on `InterceptorExecutor` (same assembly).

### The chain partition

`CreateWriteInterceptorFunction` (`InterceptorSubjectContext.cs:288-294`) partitions the resolver's output at chain compile time: all non-`ILifecycleInterceptor` write interceptors in resolved order, then the `ILifecycleInterceptor` instances. This applies only to write-chain compilation; `GetServices<IWriteInterceptor>()` query results keep the resolver order. Attributes are not used for this because ordering attributes are class-level and apply to every interface resolution; forcing `[RunsLast]` on `LifecycleInterceptor` would also move its `ILifecycleHandler` slot, breaking the documented handler seam where `SourceMonitor` and `HostedServiceHandler` run `[RunsAfter]` it (`docs/design/tracking-lifecycle.md`, "Handler Order").

Consequence, stated honestly: a write interceptor can no longer run between the lifecycle and the terminal. No first-party interceptor does (all order before it, citations in section 1). A third-party interceptor that today lands after the lifecycle got there by accident of insertion order, and its position was the deadlock trap; on master the equivalent position still ran outside the lifecycle's lock because master locked after `next()`. Pinning the lifecycle last restores master's guarantee that no registered interceptor ever runs under the topology lock. `OwnershipGraph.ReleaseUnusedClaims`'s downstream-suppression note (`OwnershipGraph.cs:494-497`) becomes vacuous for interceptors but stays for the throwing terminal and normalizing setters.

### Interface cleanup

`ILifecycleInterceptor.EnterStructuralWriteGate`/`ExitStructuralWriteGate` (`src/Namotion.Interceptor/Interceptors/ILifecycleInterceptor.cs:40-46`) lose their only production caller (`InterceptorExecutor.cs:275,291`). Remove both members: keeping never-called SPI members would misdocument the protocol. This touches the fake lifecycles in roughly ten test files (grep `EnterStructuralWriteGate` under `src/*Tests`) and the Core `PublicApi` snapshot. This is an SPI surface reduction inside a PR that already carries 22 breaking changes; it adds no consumer-visible constraint on behavior, it removes an obligation.

## 3. The four hard constraints

**(1) Pinned state (`c78328af`).** Preserved and strengthened. The structural route still pins one `ContextState` and threads it into `ExecuteInterceptedWrite(ContextState, ...)`. The property the commit established, "the routing decision and the chain resolve from the same state", now holds trivially: the executor no longer makes a separate routing decision (no `TryGetServiceFromState<ILifecycleInterceptor>` pre-resolution), the chain content is the decision. A lifecycle registered after the pin is invisible to the in-flight write as a whole and seen by the next write, exactly as today (`InterceptorExecutor.cs:262-266` comment). The inversion the commit fixed (a chain lifecycle taking the gate inside a held monitor) cannot recur because no monitor is held when the chain runs.

**(2) The ordering guarantee** (`IInterceptorExecutor.cs:77-93`): an attach or detach racing a structural write orders against it rather than failing it; only a persistent conflict throws, before the backing field is written.

- Claim-before-write is untouched: `ClaimProposedComponent` still runs before `next()` under the gate (`LifecycleInterceptor.cs:139-141`), and the foreign-context throw still happens before any backing mutation (`LifecycleInterceptor.cs:179-185`).
- A transition racing the write orders through one of three mechanisms, all of which end in the write completing or retrying, never throwing: (a) lifecycle-mediated transitions of an attached subject wait on the gate the write section holds; (b) transitions landing between routing and the gate or terminal flip the staleness check and the write re-routes against the fresh attachment (a retry is evidence of a completed transition elsewhere, so the loop is livelock-free by the same argument the design doc already makes; it remains not starvation-free, unchanged); (c) a mid-write release of the writing parent by same-thread depth-zero user code hits the reconcile-entry ownership check and the write commits without publishing edges (`StructuralReconciler.cs:187-200`), which is today's documented behavior.
- Empirical: the existing ordered-not-failed stress tests (`StructuralWriteLockOrderTests.cs:38-119`, 3000 iterations of writes racing parent removals, asserting zero exceptions and a consistent settled graph) pass unchanged under the prototype.

**(3) The documented total lock order** (gate, then attachment monitor, then SyncRoot; `docs/design/tracking-lifecycle.md`, "Lock Ordering"). Every acquisition edge in the new shape respects it: gate then monitor (claims and the structural terminal under the gate), monitor then SyncRoot (checking terminal), gate then SyncRoot (reread through the read terminal, `ReadInterceptorFactory.cs:22`). No path acquires monitor before gate anymore because no monitor is held when a chain (which contains the gate-taking lifecycle) starts. The order's statement simplifies; its direction never inverts.

**(4) The full suite passes.** Prototype evidence below: 3,460 tests run, four deterministic failures, each of which pins the old lock scope itself and is rewritten by this design (section 7), plus one known-class flake that passes standalone. No other behavior moved, which is direct evidence the wide scope was not load-bearing for anything else. Constraint 5 (no new `InternalsVisibleTo`) is satisfied: everything the design needs crosses only boundaries that already exist (`Namotion.Interceptor.csproj:15-18` already grants Core internals to Tracking, and no new grant is added).

## 4. How reconciliation moves

It does not move. Reconciliation stays inside `LifecycleInterceptor.WriteProperty`, inside the chain, under one continuous gate hold spanning [validate, claim, terminal commit, reread, reconcile, release-unused-claims] (`LifecycleInterceptor.cs:128-155`). What moves is everything else out from around it:

- The executor's outer gate and monitor hold (`InterceptorExecutor.cs:265-292`) is deleted, so upstream interceptors' pre- and post-`next` segments, subscriber dispatch (`PropertyChangeInterceptor`, upstream by `PropertyChangeInterceptor.cs:23`) and derived cascades (`DerivedPropertyChangeHandler`, upstream by `DerivedPropertyChangeHandler.cs:20`) run with no library lock held.
- The chain partition guarantees `next()` inside the gate is the terminal alone, so no registered interceptor runs inside it either.

Reconciliation orders against attach and detach exactly as before: they serialize on the same gate (`LifecycleInterceptor.cs:271,304`). The cascade re-entry path stays deliberately scalar (`InterceptorExecutor.cs:341-366`); its old justification ("the trigger may already hold the attachment monitor") disappears, but the semantic one stands: derived properties never carry edges (`LifecycleInterceptor.cs:108`).

## 5. The three related findings

**Claim/discovery race: fix, in this design.** Confirmed as described: `DiscoverComponent` reads getters of unattached subjects with no synchronization (`OwnershipGraph.cs:437`), the unattached write validates nothing (`InterceptorExecutor.cs:313-321`), and a foreign-context subject written into the component between discovery and `TryClaimDiscovered` (`LifecycleInterceptor.cs:179`, `:352`) surfaces as a throw from `AttachEdge` mid-publication (`AttachTraversal.cs:56-60`), leaving claimed-but-unowned members and committed baselines (`OwnershipGraph.cs:192`) that `DetachSubjectFromContext` does not clean beyond the root's own claim (`LifecycleInterceptor.cs:312-317`). Two mechanisms close it, both under the gate the attach already holds:

1. The checking terminal on the unattached route (route 3) closes the post-claim window: any unattached-routed write that would commit after the subject was claimed fails its `AttachedContext == null` check and re-routes through the attached protocol, where the gate (held by the attacher through claim and seed) blocks it until the descent completes and validation applies.
2. A verify-to-fixpoint step inside `TryClaimDiscovered` closes the discovery-to-claim window: after claiming the discovered set, reread the claimed subjects' structural getters; every occurrence that is not already claimed, owned, or attached to this context is validated and claimed and itself reread; a foreign-context occurrence releases every claim this operation made and throws **before any publication**, restoring "a rejection leaves no residue" (`LifecycleInterceptor.cs:341-343`). The loop terminates because each round pins new subjects and a new round requires a racing commit that landed before its subject was claimed; sustained hostile churn extends it, which is the same starvation caveat the write retry loop already documents. Because both windows are closed, seeding can no longer encounter a value discovery did not validate, so the mid-publication throw in `AttachEdge` becomes unreachable on this path (it stays as a defense assertion). The same `TryClaimDiscovered` serves `ClaimProposedComponent` (`LifecycleInterceptor.cs:179`), so the write path's claim gets the same closure for free.

**Unattached writes bypass the terminal: fix, in this design.** Route 3 sends them through the zero-interceptor chain, restoring `SyncRoot`, the commit revision and `SetWriteState` (`WriteInterceptorFactory.cs:19-41`), matching the unattached scalar route (`InterceptorExecutor.cs:223`) and master. Cost: one uncontended `SyncRoot` plus bookkeeping on a route no named benchmark measures.

**The narrowed-`TProperty` claim: the doc is false today, and this design makes it true.** The claim at `IInterceptorExecutor.cs:87-88` ("the lifecycle still takes its own gate inside the chain, so ownership stays consistent") holds only while the routing saw an attached context. A narrowed write racing an attach of the same subject routes through the scalar branch, reads the attachment as null, and commits through the zero-interceptor chain with no monitor and no revalidation (`InterceptorExecutor.cs:218-231`): the attach's seeding can read the getter before that commit lands, and the committed subject value is then never claimed by any lifecycle, a silent lost edge. Under this design the unattached route's always-checking terminal closes exactly that window (the commit either precedes the claim, and the monitor ordering makes seeding see it, or the check fails and the retry routes attached, where the in-chain lifecycle validates on the declared type). The attached half was already sound and stays sound (gate in the chain). The doc sentence gets rewritten to describe the retry semantics instead of the current false claim. Residual, documented: transitions performed through raw `TryUpdateAttachment` while a narrowed **attached** write is mid-chain are ordered by the gate only for lifecycle-mediated transitions; raw SPI callers own their ordering, as they do everywhere else.

## 6. Alternatives considered and rejected

**(a) The cheap option: keep the scope, refuse a second gate.** Track gate ownership per thread; a structural write that would take context B's gate while holding context A's throws instead of deadlocking. Rejected. It converts both repros from hangs into new runtime exceptions for patterns that work on master, which is precisely the outcome ruled out: a 23rd, silent, consumer-visible constraint. It also does nothing for Repro B without additionally refusing the monitor, which would break the innocent lifecycle-free cross-subject pattern entirely. It treats the symptom and forfeits the stated goal (an internal fix). It does not win on any axis except implementation size, and the prototype shows the internal fix is itself small.

**(b) Master's shape: `next()` first, lock and reread after.** Rejected because it surrenders both halves of what the branch bought: validation would again happen after the backing write (no "throws before the backing field is written"), and the reread becomes a racy convergence mechanism again, the exact window the maintainer identified as the reason neither endpoint is acceptable.

**(c) Global lock ordering across contexts (rank gates by identity, acquire in rank order).** Rejected as impossible in principle here: the second context is discovered inside user code mid-chain, so the writer cannot know the full lock set up front, and Repro B's monitors are per-subject and consumer-ordered, so no static rank exists to acquire them in.

**(d) Narrow the executor's hold but keep the lifecycle mid-chain (no partition).** Rejected: fixes Repro B only. Repro A's interceptor sits downstream of the lifecycle and still runs its cross-write inside the gate held across `next()` (`LifecycleInterceptor.cs:128-155`); verified against the resolver's insertion-order rule (`InterceptorSubjectContext.cs:346-350`).

**(e) Split the lifecycle's gate hold (claim under gate, release during `next()`, retake for reconcile).** Rejected: it reintroduces master's window in a new place. Another thread's commit to the same property can land between this write's commit and its reconcile, so the reconcile input decouples from the write again and edges transiently track a value the backing store no longer holds; worse, a detach-plus-reattach can interleave the two sections wholesale, and the claim set becomes visible to a second context's attach as "owned by C" while only provisional, producing spurious cross-context throws that violate "only a persistent conflict throws". The continuous gate hold with a terminal-only `next()` gets the same deadlock-freedom without any of this.

## 7. Test plan

**Pinning the new behavior (exist already, must pass unchanged):** the two repros (`GateChainDeadlockRepro.cs`, `MonitorAbbaRepro.cs`, moved from the sibling worktree into the tree as permanent concurrency tests; they pass in about 50 ms under the prototype, timeouts untouched); the lock-order stress pair (`StructuralWriteLockOrderTests.cs:38-119` and the sibling test, 3000 iterations, assert ordering-not-throwing plus settled consistency); the whole remaining suite (3,460 tests), which the prototype passes minus the four below.

**Tests that pin the old scope and must change (all four verified failing under the prototype, each with the exact reason):**

- `StructuralWriteTests.WhenConcurrentDetachRacesAStructuralWrite_ThenTheDetachWaitsAndBothComplete` (`src/Namotion.Interceptor.Tests/StructuralWriteTests.cs:172`, failing assert at `:218`). Pins "a raw detach blocks while a write is parked mid-chain". The new contract is the opposite ordering with the same outcome: the detach completes immediately, the parked write's terminal detects the move and retries, the write still commits (its final-state asserts, write committed and detach landed, already pass under the prototype). Rewrite to assert: detach does not wait, writer neither throws nor loses the write, settled state consistent.
- `StructuralWriteTests.WhenLifecycleIsRegisteredWhileAStructuralWriteWaitsForTheMonitor_ThenThatWriteSeesItNowhere` (`StructuralWriteTests.cs:232`, failing assert at `:304`). The pinned-state property survives and stays asserted (`probe.WritePropertyCount == 0` for the raced write); the mechanic (parking the raced writer on the pre-chain monitor) and the follow-up assertion (`GateEnterCount == 1`) no longer exist. Rewrite the window mechanic to park the in-flight write inside its own chain via the existing `GatingWriteInterceptor`, register the probe, and assert the in-flight write sees it nowhere while the next write sees it in the chain (`WritePropertyCount`), dropping the gate-count assertions with the removed members.
- `HandWrittenSubjectWriteTests.WhenHandWrittenSetterAssignsASubjectTypedProperty_ThenTheWriteTakesTheLifecycleGate` and `DynamicPropertyWriteRoutingTests.WhenDynamicPropertyDeclaredTypeCanContainSubjects_ThenWriteTakesTheLifecycleGate` (`src/Namotion.Interceptor.Tests/HandWrittenSubjectWriteTests.cs`, `src/Namotion.Interceptor.Registry.Tests/DynamicPropertyWriteRoutingTests.cs:28`). Both count `EnterStructuralWriteGate` calls on a fake lifecycle to prove the structural route engaged. The surviving Core-seam guarantee is "the lifecycle participates in the chain for this write"; re-express both as `WriteProperty`-observed assertions on the fake.

**New tests this design requires:**

- Terminal retry: a raw `TryUpdateAttachment` transition landing while a structural write is parked mid-chain in a lifecycle-free context; assert the write commits via retry, the transition never waits, no exception (the ordering guarantee at the SPI level).
- Retry preserves origin: a source-stamped write that is forced to retry keeps `ChangeOrigin.FromSource` on the committed state.
- Claim-verify fixpoint: an unattached structural write into a component racing that component's attach, driven deterministically (park the attach between discovery and claim with a hook or with the seed-side `GatingWriteInterceptor` pattern); assert either full ownership or a pre-publication rejection with zero residue (subject unattached, no baselines: `HasBaseline` exists for exactly this, `OwnershipGraph.cs:131-134`).
- Unattached terminal restoration: an unattached structural write increments the commit revision and publishes write state (mirrors the existing attached assertion at `StructuralWriteTests.cs:166-168`).
- Chain-partition pin: an unattributed third-party write interceptor registered after `WithFullPropertyTracking` observes `next()` returning with the reconcile already done (it runs upstream of the lifecycle), and its post-`next` cross-context structural write completes (Repro A is the concurrency version; this is the deterministic single-thread version).
- A cross-context randomized stress in the style of `StructuralWriteLockOrderTests`: two lifecycle contexts, writers cross-writing after `next()`, attach/detach churn, bounded joins, zero exceptions, consistent settled graphs.

**Known flake, not this design:** one `Namotion.Interceptor.Connectors.Tests` failure appeared once under full-suite parallel load and passed standalone (732/732); it matches the pre-existing full-suite-load flake class already tracked for that assembly. The implementer must confirm it reproduces on the unmodified branch before attributing it.

**Benchmarks:** `LifecycleOwnershipBenchmark` and `RegistryBenchmark` (`SetScalarAttached` ~167 ns, `Write` ~1.03 us, `ReplaceSingleChildReference` ~2.68 us) via `pwsh scripts/benchmark.ps1` against the branch base, per `docs/benchmarking.md`. Expected: scalar attached unchanged (route untouched; one predicted-not-taken loop branch); structural attached neutral to slightly better (the outer gate enter/exit and monitor hold are removed, one monitor acquisition moves into the terminal, gate hold duration strictly shrinks); unattached structural slightly slower by one uncontended monitor plus terminal bookkeeping, a correctness restoration on an unbenchmarked route. Any regression on the named benchmarks above noise gates the merge per repo policy.

## 8. Prototype evidence, residual risks, and what could not be determined

**Prototype.** A throwaway prototype of routes 1-3 (chain partition, executor loop, checking terminals, lifecycle staleness retry) lives uncommitted in this worktree, every hunk marked `PROTOTYPE (throwaway)`, in `InterceptorExecutor.cs`, `WriteInterceptorFactory.cs`, `IWriteInterceptor.cs`, `InterceptorSubjectContext.cs`, `LifecycleInterceptor.cs`. It is evidence for this design's feasibility claims, not the implementation; per this project's practice the implementation is re-derived from this document. It omits the claim-verify fixpoint, the origin-preserving retry, the per-chain terminal-flavor selection (it branches per write instead), and the interface cleanup. Results: both repros pass in ~50 ms; full unit suite 3,460 tests with exactly the four expected scope-pinning failures; concurrency category stable across repeated runs; the two long-running registry stress tests show no standalone timing change against the unmodified branch (17-19 s vs 16 s baseline; an initial 48 s reading was parallel-suite interference, reproduced as such).

**Residual constraints, unchanged or narrowed versus today, to document rather than fix here:**

- User code invoked from inside the gate by the reconcile itself (collection/dictionary implementations, dictionary-key `Equals`, read interceptors during the reread) must not structurally write into a different context. Identical exposure existed on master inside its lock; the callback contract covers callbacks; nothing covers these except documentation, before and after this design.
- A registry dynamic property's stored setter executes at the terminal under monitor and SyncRoot (and the gate on route 1). Branch status quo, narrower than today's scope, wider than master (master ran terminals before its lock). A stored setter performing a foreign-context structural write remains undefined behavior; document on `AddProperty`.
- The write retry loop and the claim-verify loop are livelock-free but not starvation-free under adversarial attach/detach churn, the same caveat the current design doc records for the routing retry.

**Not determined, and the experiment that settles each:**

- Whether any external consumer relies on a write interceptor ordered after the lifecycle observing pre-reconcile state. In-repo, nothing does (grep for `RunsAfter(typeof(LifecycleInterceptor))` over `IWriteInterceptor` implementers is empty). Externally unknowable; the PR description must call out the partition as a behavior note.
- Whether the one-time connectors flake is the known pre-existing one: run that test class 50x on the unmodified branch under full-suite load and compare signatures.
- The exact perf delta: the numbers above are reasoning plus test-suite timing, not benchmark runs. The benchmark comparison in section 7 is the gate, run per `docs/benchmarking.md` with the pinned-CPU recipe.
- Whether `TryGetAttachment`'s monitor-taking snapshot has callers that would now block briefly behind terminal commits (the monitor gains short hold windows at commit time). Callers are transition sites and `AttachSubjectToContext`/`DetachSubjectFromContext` validation reads (`LifecycleInterceptor.cs:274,307`); all are cold paths, but the implementer should re-grep after rebasing.
