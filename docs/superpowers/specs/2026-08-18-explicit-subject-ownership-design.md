# Explicit Subject Ownership and Lifecycle Design

**Date:** 2026-08-18

**Status:** Approved design for PR #419

**Roadmap:** `2026-08-17-single-effective-context-stack-roadmap.md`

## Purpose

PR #419 replaces fallback-driven lifecycle attachment with strict explicit roots, one configured-context ownership domain, one effective ownership route, prospective structural admission, and one permanent Core membership ledger. It merges recursive inheritance into the exact single lifecycle coordinator resolved for the ownership domain and makes public fallback mutation service composition only.

This design is governed by the roadmap's [stack-wide acceptance criterion](2026-08-17-single-effective-context-stack-roadmap.md#stack-wide-acceptance-criterion). That criterion is stated only in the roadmap. Every wait, restart, persistent failure, and unsupported liveness condition below is interpreted through it.

## Terms and Invariants

- **Explicit anchor:** one root relationship created by `AttachToContext` and removed only by exact `DetachFromContext`.
- **Parent membership:** one committed structural `PropertyReference` that currently reaches a child. Repeated occurrences in one collection or dictionary property are one Core membership; Tracking retains occurrence indices for projections.
- **Ownership domain:** the exact plain configured `InterceptorSubjectContext` supplied to a root, compared by reference.
- **Effective route:** PR #474's exact immutable descriptor targeting the selected parent executor or explicit configured context.
- **Route identity:** Core's opaque allocation-free equality capability for one exact routed descriptor or one exact route-free epoch. It exposes neither a descriptor nor a route target.
- **Lifecycle coordinator:** the zero-or-one exact `ILifecycleInterceptor` instance captured for an active ownership domain by `ReferenceEquals`. `WithLifecycle()` installs the supported official Tracking coordinator, which is also the reference-identical `ILifecycleHandler` occupying the logical coordinator slot.
- **Topology turn:** the process-wide reentrant `OwnershipTopologyGate` interval serializing potentially structural and topology mutation.
- **Tentative batch:** an all-or-nothing `Preparing` set of proposed anchor, parent, domain, generation, route, and baseline changes.
- **Coordinator invocation:** one exact entry into the selected lifecycle coordinator. It may contain several uninterrupted settlement segments but has one final provider release.
- **Settlement segment:** the uninterrupted portion of one coordinator invocation between topology-visible nested operations. Ordinary repeated downstream terminals coalesce inside one segment; a mandatory settlement barrier ends the segment before supported nested topology work selects an action.
- **Committed operation:** the exact immutable generation delta for one settlement segment exposed to Tracking only after Core incoming-ledger publication.
- **Private property/state monitor:** the one monitor owned by a subject's `InterceptorExecutor`. It replaces public `IInterceptorSubject.SyncRoot` and is never exposed as a synchronization contract.

The permanent invariants are:

1. A subject has zero or one explicit anchor, one ownership domain, one selected route, and one checked monotonically increasing ownership generation that never wraps or resets.
2. Core parent membership is keyed by exact `PropertyReference`; repeated collection occurrences do not multiply the Core reference count.
3. An explicit anchor wins route selection. In a lifecycle-coordinated domain, the earliest surviving compatible acyclic parent membership otherwise wins. A coordinator-free domain never creates parent membership.
4. Public fallbacks compose services only. They do not create an anchor, membership, lifecycle callback, or ownership route.
5. Every active effective context resolves zero or one exact lifecycle coordinator identity using `ReferenceEquals` only. Repeated paths to the same instance collapse; two distinct instances are permanently incompatible even when `Equals` returns true.
6. In a lifecycle-coordinated domain, backing structural values, Core membership, Tracking baseline, route, Registry/parent projection, and callbacks agree after a successful operation settles. In a coordinator-free domain, only an explicit root route is owned and structural setters are ordinary intercepted writes.
7. Cycles, shared DAGs, compatible multiple parents, repeated paths, and final component release remain supported.
8. Core alone enters the topology turn, reserves, commits, cancels, restarts, and finalizes. Tracking traverses, reserves through the facade, selects parents, pins callback arrays, and reconciles committed state. For property-carried first attach and final release, Tracking chooses the logical coordinator slot at which Core publishes or clears the already committed selected route. Core itself preserves explicit-root entry visibility by publishing the configured-context route after commit and before root attach phase 1, and by clearing the old route only after root detach phases 1 through 6 complete.
9. Ownership planning is incremental. Core's committed incoming ledger and Tracking's committed outgoing subject/property baseline are the only persistent graph indexes. A structural operation must not clone either ledger or enumerate the whole rooted graph to derive a local prospective result.
10. Ownership generations, route-free epochs, and opaque coordinator-invocation and settlement-segment identity counters use checked monotonic increments and never silently wrap. Exhaustion is persistent until committed observable state or arguments change in a way that no longer requires that next identity; it is not transient contention, stale state, or retry control flow.
11. During an active committed-but-unpublished route transition, topology-bearing nested action and structural-chain selection use Core's exact guarded committed overlay, while ordinary service resolution preserves the callback phase's publicly published route. Overlay chains never enter public immutable caches.
12. A nested operation that would truly invert the same subject's ownership transition while that subject's exact lifecycle callback obligation is executing is a stable programming-contract failure before nested effects. Other-subject and same-subject noninverse nesting remain supported.

## Advanced Public Lifecycle Facade

Core and Tracking are separate packages but already have friend access, so public visibility is not technically required for official Tracking to compile. The maintainer deliberately retains the existing public `ILifecycleInterceptor` seam and the capability-minimal public operation, view, context, and opaque identity types instead of creating a parallel internal interface, adapters, or duplicate protocol. This is advanced versioned public API tracked by exact Public API snapshots. Documentation discourages third-party implementation; official packages may make breaking changes only through the repository's normal package breaking-change and version policy. No new `InternalsVisibleTo` entry or `EditorBrowsable` suppression is added.

The capability-minimal surface is:

```csharp
public interface ILifecycleInterceptor : IWriteInterceptor
{
    void PrepareSubjectAttachment(
        IInterceptorSubject subject,
        IInterceptorSubjectContext context,
        ref SubjectOwnershipOperation operation);

    void PrepareSubjectDetachment(
        IInterceptorSubject subject,
        IInterceptorSubjectContext context,
        ref SubjectOwnershipOperation operation);

    void PrepareSubjectPropertyWrite<TProperty>(
        ref SubjectOwnershipWriteContext<TProperty> context,
        ref SubjectOwnershipOperation operation);

    void PrepareSubjectMetadataAdditionBatch(
        ref SubjectMetadataAdditionBatchContext context,
        ref SubjectOwnershipOperation operation);

    void ReconcileSubjectOwnership(ref SubjectOwnershipOperation operation);

    void ReleaseSubjectOwnership(ref SubjectOwnershipOperation operation);
}

public readonly ref struct SubjectOwnershipWriteContext<TProperty>
{
    public PropertyReference Property { get; }
    public TProperty ProposedValue { get; }
}

public readonly ref struct SubjectMetadataAddition
{
    public SubjectPropertyMetadata Metadata { get; }
    public object? CurrentValue { get; }
}

public readonly ref struct SubjectMetadataAdditionBatchContext
{
    public IInterceptorSubject Subject { get; }
    public int Count { get; }
    public SubjectMetadataAddition GetAddition(int index);
}

public readonly ref struct SubjectOwnershipView
{
    public IInterceptorSubject Subject { get; }
    public IInterceptorSubjectContext? ExplicitAttachContext { get; }
    public IInterceptorSubjectContext? OwnershipDomain { get; }
    public PropertyReference? SelectedParent { get; }
    public long Generation { get; }
    public SubjectOwnershipRouteIdentity RouteIdentity { get; }
    public int PropertyCount { get; }
    public SubjectPropertyMetadata GetProperty(int index);
    public int ParentMembershipCount { get; }
    public PropertyReference GetParentMembership(int index);
}

public readonly struct SubjectOwnershipRouteIdentity
{
    public bool IsSame(in SubjectOwnershipRouteIdentity other);
}

public readonly struct SubjectOwnershipOperationIdentity
{
    public bool IsSameInvocation(in SubjectOwnershipOperationIdentity other);
    public bool IsSameSegment(in SubjectOwnershipOperationIdentity other);
}

public readonly ref struct SubjectOwnershipOperation
{
    public SubjectOwnershipOperationIdentity Identity { get; }
    public bool IsPreparationCancelled { get; }
    public IInterceptorSubjectContext OwnershipDomain { get; }
    public SubjectOwnershipView GetView(IInterceptorSubject subject);
    public bool IsCurrent(in SubjectOwnershipView view);
    public void ReserveParentAddition(PropertyReference property, IInterceptorSubject child);
    public void ReserveParentRemoval(PropertyReference property, IInterceptorSubject child);
    public void ReserveFinalRelease(IInterceptorSubject subject);
    public void SelectActiveParent(IInterceptorSubject subject, PropertyReference? parent);
    public ImmutableArray<TService> GetCurrentServices<TService>(IInterceptorSubject subject);

        in SubjectOwnershipView committedView,
        out SubjectOwnershipRouteIdentity resultingRouteIdentity);

{
    public static SubjectMetadataCommitRegistration Register(
        IInterceptorSubject subject,
        Action onCommitted);

    public void Dispose();
}
```

The batch context is a count/index view over Core's once-materialized metadata array and parallel current-value slots. It adds no enumerable, array copy, or provider-frame allocation. `CurrentValue` may box a value-type structural candidate because `AddProperties` is cold; the no-boxing requirement applies to warmed generic structural writes and their provider state.

`SubjectOwnershipView.PropertyCount` and `GetProperty(index)` are an allocation-free indexed view over the subject executor's exact committed metadata publication snapshot. They neither enumerate nor copy metadata. The returned metadata is the exact committed instance at that index. Official Tracking uses only this indexed view for canonical property traversal; it never derives traversal order from `IInterceptorSubject.Properties`, `IReadOnlyDictionary`, `FrozenDictionary`, or any dictionary enumeration.

`SubjectOwnershipRouteIdentity` declares no public constructor, field, equality operator, ordering, conversion, route target, or descriptor accessor; `IsSame(in other)` is its only declared comparison operation. It is true only for two valid identities denoting the same exact issued route epoch. Staleness does not rewrite value equality, but a default, value copied outside the matching synchronous coordinator lifetime, or otherwise fabricated value authorizes nothing and never passes a Core guard. Its private Core-owned representation may carry the exact immutable routed-descriptor reference needed for allocation-free equality and guards. That physical reference does not make the descriptor public or provider-semantic: official Tracking may only copy the opaque value, compare it with `IsSame`, return it to constrained Core guards, and clear the identity and any contained reference at final release. It never exposes, casts, semantically inspects, or manipulates the descriptor. Route-free identity uses only its scalar Core epoch and contains no descriptor reference.

The two generic service methods return exact immutable-array references. `GetCurrentServices` pins the array from the exact currently published executor snapshot. `GetProspectiveServices` resolves once during preparation against that snapshot plus the proposed route target/domain, without creating or publishing a routed `ContextState`; official Tracking retains that prospective array only in its pooled frame. These already approved methods remain part of the deliberately public advanced facade and avoid a parallel internal service-view adapter. No additional public typed service-view wrapper, coordinator-rank value, or service-walk API is required. `GetParentMembership(index)` is a zero-allocation index API over Core's inline-first membership storage. `IsCurrent(in view)` is the minimum constrained current-state guard: it returns true only when the Core-issued view's exact subject, generation, and route identity all still match committed state in the active synchronous operation. It returns false for default, fabricated, released, or mismatched views and reveals no current descriptor or target. A false result is an observation for exact obligation classification, not permission by itself to suppress an owed phase.

PR #474's foundation service materialization must be corrected before PR #419 builds on it. Every immutable service, interceptor-chain, lifecycle-handler, and property-handler materialization deduplicates by reference identity, never `Equals`: repeated discovery of the same exact instance through one or several paths collapses to its first ordered occurrence, while distinct instances remain distinct in order even when either instance reports value equality. Coordinator candidate collection likewise uses `ReferenceEquals` only. Two distinct `ILifecycleInterceptor` instances therefore reject even when `Equals` says equal, and an equality-colliding noncoordinator service cannot erase the coordinator, another handler, or an interceptor chain node. This reference-identity correction belongs to the PR #474 foundation and is a prerequisite for PR #419; this document does not amend PR #474's separate specification or code.

Core assigns an exact identity to every routed descriptor and an exact Core-owned epoch identity to route-free state. An unchanged exact descriptor preserves its identity across ownership generations and callback-silent source changes. Any changed descriptor receives a different identity even when it resolves to the same target. Clearing a route produces a route-free epoch distinct from the prior routed identity and from every prior identity that can still be presented within an authorized synchronous lifetime; remaining route-free without a route transition preserves the current epoch. The route-free identity is scalar Core state and requires no `ContextOwnershipRoute`, routed `ContextState`, descriptor exposure, or managed allocation.

`TryPublishCommittedRoute` is deliberately acknowledged as one narrowly constrained commit-phase capability. Core creates the committed view only after ledger commit. The method accepts only the exact subject, committed generation, and old route identity carried by the currently owed coordinator publication phase, only while Core is invoking that matching phase, and at most one call can publish. An official Tracking call in any other phase or with a fabricated/mismatched view throws a persistent `InvalidOperationException`. An older generation is not by itself permission to drop an owed publication: the call returns `false` as a stale no-op only after an exact later operation has superseded/adopted that obligation because its route-identity dependency is no longer valid. On `true`, `resultingRouteIdentity` is the exact identity of the resulting published route; on `false`, it is default and authorizes nothing. Core still owns validation, ledger commit, retry, cancellation, generation, obligation classification, descriptor materialization, and final cleanup. Reflection tests inspect these capabilities and guards rather than method names and verify the opaque identity, constrained current guard, out identity, and allocation-free count/index metadata traversal, with no descriptor, route-target, enumerable, or dictionary-order capability.

`SubjectOwnershipOperationIdentity` is one opaque allocation-free Core-issued value containing an exact coordinator-invocation identity and exact settlement-segment epoch. `IsSameInvocation` is true for ordinary downstream repeats and later segments in one coordinator entry and false for upstream repeats or synchronous nested coordinator entries. `IsSameSegment` is true only while those calls belong to the same uninterrupted segment. A default, copied-after-release, or otherwise fabricated value authorizes nothing and compares false. There is no public constructor or field. Official Tracking may copy the exact value only into its synchronous LIFO frame until the matching final `ReleaseSubjectOwnership`; it must not retain it afterward or use it to construct another operation. `IsPreparationCancelled` is the only preparation-cancellation observation capability. After any reentrant application call, official Tracking checks it before further traversal or reservation and returns normally when it is true. Cancellation is not exposed as an exception or retry result.

After `IsPreparationCancelled` becomes true, `Identity` and the cancellation flag remain readable. `GetView` exposes the then-current committed ownership generation, exact route identity, and exact committed metadata order through `PropertyCount`/`GetProperty`; no proposed route or metadata addition appears. `IsCurrent` evaluates that committed view normally. `GetCurrentServices` exposes current published services, and `GetProspectiveServices` returns that same current immutable array because the proposal no longer exists. Reservation and selection methods are no-ops, and `TryPublishCommittedRoute` returns `false` with a default resulting identity. Official Tracking still must cease application traversal immediately; continuing violates the official infrastructure contract, but subsequent facade calls cannot mutate library state or produce a timing-dependent exception.

`SubjectMetadataCommitRegistration` is the smallest separate commit-identity seam. `Register` pushes one exact thread-local token for the next `AddProperties` entry on that subject. Core claims that token into the outer operation immediately on entry, before input enumeration or any enumerable reentrancy, invokes its callback exactly once immediately after the metadata lookup, ordered snapshot, and ownership ledger commit and before reconciliation/user callbacks, and disposes or restores the previous token in `finally`. A precommit rejection never invokes it. A nested Registry call pushes and claims a distinct token; a nested unregistered Core call cannot steal the already claimed outer token. Equal or same-name metadata never participates in identity. The callback is an advanced synchronous no-retain/no-reentry/no-throw hook; official Registry performs its exact wrapper promotion as its commit action and exposes no application callback from this seam. If the notification nevertheless throws after commit, Core captures its first EDI without replaying the token, continues the complete committed reconciliation/finalization protocol below, and rethrows according to the established precedence.

Tracking keeps its operation state in a thread-static pooled LIFO frame keyed by the exact Core-issued invocation identity. Each public attach, detach, lifecycle-coordinator write invocation, or metadata batch prepare pushes exactly one invocation frame. Repeated structural terminals downstream of one coordinator reuse that frame and, until a settlement barrier, the same segment epoch; repeated calls upstream and synchronous nested coordinator invocations have different invocation identities and push separate frames. `ReconcileSubjectOwnership` may be called at several mandatory settlement checkpoints in one invocation, once for each committed segment, and retains the invocation frame for a later segment epoch. Core calls `ReleaseSubjectOwnership` exactly once when the whole invocation finally ends, whether it succeeded, experienced any number of attempt cancellations/restarts, or unwound through a precommit, reconciliation, or finalization exception; Tracking then pops, clears every reference and identity, and returns buffers. An internal attempt restart without a topology-visible nested operation does not manufacture an invocation, release, or callback boundary.

No library-invented boxed enumerator crosses this facade, and no catch-all `object` provider payload, operation enum/runtime switch, or visually minimized method set is accepted when it adds allocations or broadens capability. Enumeration performed by an arbitrary supplied collection fallback is not part of this facade and follows the supplied-container rule below. Official package implementations must not retain any facade, view, write context, metadata context, membership value, callback array, or registration callback beyond the synchronous scope. Prepare and release methods must be concurrency-safe across threads and exception-free after input validation. There is no `EditorBrowsable(Never)` annotation and no new friend declaration. The surface remains advanced versioned public API for the official package stack; third-party implementation is discouraged and official breaking changes follow normal package policy rather than an untracked private-contract change.

## Numeric Identity Exhaustion

Core issues ownership generations, route-free epochs, coordinator-invocation identities, and settlement-segment identities with checked monotonic increments. None silently wraps, resets, aliases a prior value, or falls back to a fabricated/default identity. Routed descriptor identity remains the exact descriptor identity already specified above and does not add a numeric counter merely to share this rule.

Under `OwnershipTopologyGate`, Core checks and reserves each next numeric identity at the earliest point its scope is known. An initial coordinator-bearing call reserves its invocation and initial segment identities before official Tracking receives the operation for preparation and before its terminal writer can run. Final semantic validation then establishes the exact affected set and reserves every affected next ownership generation before the initiating writer. A route clear that needs a new route-free epoch reserves it during that precommit validation, before any lifecycle callback, while immutable route/state materialization still remains deferred to its approved publication phase. A later segment reserves its next segment identity before official Tracking receives that segment or any effect occurs in it. A synchronous nested invocation performs the same reservation before its own action selection can produce an effect. Thus exhaustion is detected before the rejected action performs a backing-store mutation, lifecycle callback dispatch, route or context-state publication, Registry notification, metadata publication, or other observable ownership effect.

If any required checked increment is exhausted, Core throws ordinary `InvalidOperationException` before the action exposes any of the effects above. It publishes no reserved value and invokes no lifecycle callback. Immediate retry with identical arguments and unchanged committed observable application state fails identically because the exhausted counter remains exhausted. This is a stable resource-state failure permitted by the stack-wide acceptance criterion, not a timing-dependent retry exception. Internal or test-only seams may seed each counter near its maximum solely for deterministic boundary tests; they expose no public mutation capability.

When one coordinator invocation already settled an earlier segment, that segment remains a valid prior serial result. Exhaustion while a later segment or nested invocation requests its own next identity rejects only that later action before any effect of that action and does not roll back or replay the settled segment. Exception precedence treats this exhaustion as the later action's permanent precommit incompatibility; any earlier primary exception still wins under the existing precedence table.

## Global Topology Turn and Lock Order

`SubjectOwnershipCoordinator` owns one static process-wide monitor:

```csharp
internal static object OwnershipTopologyGate { get; }
```

Every potentially structural write enters it before context-state/action selection. Strict attach/detach, lifecycle preparation/reconciliation/finalization, Core ledger mutation, every PR #474 ownership-route mutation, context service/fallback mutation, and `AddProperties` enter the same monitor. `InterceptorSubjectContext.TryChangeOwnershipRoute` enters the gate itself and then `_mutationLock`; it never relies on caller ownership. The topology gate remains held through reverse registration, immutable state publication, conditional old reverse unregistration, and the complete reverse invalidation walk. `_mutationLock` is released before invalidation, preserving PR #474's leaf-lock discipline while preventing another structural operation from pinning an upstream stale chain.

The ordinary lock orders are:

```text
OwnershipTopologyGate
  -> at most one InterceptorSubjectContext._mutationLock
       -> at most one _usedByContexts leaf-set lock
  -> or at most one InterceptorExecutor private property/state monitor
  -> or at most one Tracking/Registry projection leaf lock
```

Synchronous `TryAddService` predicate/factory reentrancy is the one lower-lock exception. It may produce `OwnershipTopologyGate -> source context lock -> zero or more same-thread nested target context locks`, and nested ownership work may temporarily add one executor or feature projection leaf below that stack. All nested context locks unwind in LIFO order. No competing thread can own a target context lock before the topology gate, and no library code waits for the topology gate while holding a lower lock. Route mutation takes topology gate, one context lock, and one reverse leaf. Core ledger publication takes topology gate and one executor monitor at a time. Feature reconciliation takes one Registry or Tracking projection leaf at a time and invokes no user code under it. Reads, invokes, scalar writes, and `GetServices` never take the topology gate. A zero-interceptor read remains the current direct lock-free delegate call. Only an intercepted read terminal and scalar write terminal take the private executor monitor.

The global monitor is reentrant. Synchronous cross-domain A to B work runs inline. An external B to A caller waits before it acquires B's context or executor monitor, then rereads committed state after admission. Disconnected domains intentionally lose parallel structural and configuration throughput. They retain independent reads, scalar work, invokes, and service resolution. `Monitor` supplies exclusion and reentrancy but no FIFO or starvation guarantee. Completion claims assume finite contention and scheduler progress; sustained adversarial contention is an unsupported liveness condition and no allocation-heavy fairness queue is added.

User interceptors, lifecycle preparation/traversal, direct ownership readers, lifecycle handlers, events, property handlers, context predicate/factory callbacks, and direct backing writers run while the topology turn is owned. They do not run under a context lock or executor monitor, except:

- `TryAddService` invokes its predicate and factory under the topology gate plus the source `_mutationLock`, preserving current atomicity and state reread;
- the synchronous direct-store backing writer runs under the topology gate plus the initiating executor monitor;
- current `TryAddService` same-thread callbacks may reentrantly enter another built-in context lock because no competing thread can own that target lock before the topology gate.

Callbacks, predicates, factories, ownership readers, and custom writers must not synchronously wait for another thread whose operation needs the topology gate. Generated and built-in backing writers are direct stores. A custom writer is also required to be a synchronous direct store and must not invoke ownership, context, topology, or metadata APIs while the executor monitor is held. `IInterceptorExecutor.GetPropertyValue` XML likewise requires its delegate to be a synchronous, nonblocking direct storage read with no context, ownership, topology, or metadata call; generated and Dynamic reads comply. This is a contract-only restriction. Core adds no thread-local read guard or runtime diagnostic to a scalar/intercepted-read hot path, and deadlock avoidance is not guaranteed for an advanced delegate that violates the contract. A custom delegate that violates either reader or writer rules, including writer mutation followed by throw, is advanced caller misuse outside the library-controlled transient-failure criterion; the library does not promise rollback for that application code.

Before a supported same-thread nested structural write, attach, detach, `AddProperties`, ownership-relevant context mutation, or ownership query that requires ledger/route agreement selects any action or takes a context, executor, or feature lock, Core runs the settlement barrier for the nearest ancestor segment in `CommittedPending`. The barrier remains under `OwnershipTopologyGate`, records the Tracking baseline first, runs that segment's exact callback phases, publishes its property-carried selected routes at the logical coordinator slots, and finalizes descriptors. The nested operation then rereads the now-published state and runs in the valid serial order after that segment. Reentrancy from a barrier callback instead sees the ancestor in `Reconciling`; it cannot resettle that segment and uses the exact committed-but-unpublished action overlay below. A lock-free `GetServices` call is deliberately neither a barrier nor an overlay consumer: it observes the phase-appropriate last published immutable route.

## Committed-But-Unpublished Action Overlay

During `Reconciling`, Core's incoming ledger may already contain a committed route transition whose public immutable executor state has not reached its entry-mode publication boundary. This window includes property-carried first attach before its coordinator publication, property-carried final release before its coordinator clear, selected-parent or other committed route transfer before its coordinator publication, and explicit-root final detach before its post-phase-6 clear. True explicit-root first attach has no such window because Core publishes its configured-context route before root phase 1.

For each such affected subject, the active Core coordinator accumulator owns one synchronous committed-but-unpublished action overlay containing the exact committed subject generation, expected currently published route identity, committed selected route target/domain inputs or exact reserved route-free epoch, ownership domain/coordinator, and the immutable service/interceptor inputs required to select a topology-bearing action and its write-interceptor chain. It is derived from the authoritative committed ledger plus the then-current identity-preserving context/executor state. It does not prebuild the immutable routed descriptor or `ContextState`; those remain materialized at the approved publication boundary from the then-current immutable state. The overlay is not another attached-subject truth, public route, executor cache entry, context cache entry, or provider-owned descriptor. Tracking may retain only its already approved opaque identities and pinned callback arrays; Core alone owns the overlay and internal route inputs.

While that exact reconciliation frame is active on the current thread, a reentrant potentially structural write selects both its ownership action and its `WriteInterceptorChain<TProperty>` from the overlay before invoking any interceptor prefix. Reentrant attach/detach, `AddProperties`, ownership-relevant context mutation, and ownership queries likewise use the overlay for action selection, authority analysis, lifecycle-coordinator selection, and any interceptor/handler arrays belonging to the nested topology action. A nested operation on another affected subject uses that subject's nearest exact overlay entry. Scalar writes, reads, invokes, and ordinary `GetServices` do not consume the overlay and continue to observe the publicly published immutable state required by the callback visibility tables.

Before overlay selection, Core checks the exact subject, committed generation, expected public route identity, active invocation/segment identity, and pending publication/clear obligation. A mismatch causes Core to follow the exact later-operation adoption classification and reread the winning committed overlay or published state before any nested prefix or application effect begins. Once a nested prefix has started, internal publication, adoption, cancellation, or stale-state handling never reselects or replays that prefix, its user effects, writer, `AddProperties` input, predicate, or factory. The selected nested action either commits once against its exact guarded input or fails for an existing persistent semantic/application reason.

An overlay-resolved interceptor chain is synchronous operation state. Each overlay entry guards by reference identity every immutable `ContextState` that contributed its route, service, handler, interceptor-array, or chain input. Core may reuse the reconciliation frame's exact immutable interceptor arrays and retained chain-factory/pool capacity where their identities match; otherwise it constructs the uncommon nested chain from the overlay inputs. It never installs that chain or its derived service result in public immutable context/executor state, never writes it into an ordinary route cache, and never lets it satisfy a later public cache lookup.

When an identity-preserving context publication succeeds while an affected frame is `Reconciling`, Core uses the existing reverse dependency cone to invalidate every affected committed-but-unpublished overlay entry and immediately clears its old service, handler, interceptor-array, and constructed-chain references. The committed ledger inputs, subject/generation/route-identity guard, and pending obligation remain. Before any later nested topology prefix or action is selected through that entry, Core compares the exact contributing immutable `ContextState` identities and, when any changed, lazily rebuilds the cache-free service, handler, interceptor-array, and chain inputs from the then-current immutable states. It then reruns the exact subject, generation, route-identity, invocation/segment, and obligation guard before user code. An eager public cache insertion, new public API, or reuse of an invalidated array or chain is forbidden. The already pinned outer callback arrays remain unchanged, while the nested operation observes the successful context publication as a future operation. Publication, exact later-operation adoption, cancellation of the owning operation, and finalization clear every remaining overlay route input, contributing-state identity, service/array, chain, subject, context, and identity reference. An external caller cannot see the synchronous overlay: it waits at `OwnershipTopologyGate`, then selects from the finalized publicly published state.

The route-visible columns in the callback tables describe ordinary `GetServices` and other public immutable-state resolution. They deliberately do not describe topology-bearing nested action/chain selection during `Reconciling`, which uses the committed overlay. Thus a property-carried pre-coordinator callback may resolve ordinary services through the old/route-free public route while a structural write invoked from that callback selects the already committed new route chain. After publication, both paths converge on the same exact public route without contaminating any old or unrelated cache.

While one subject's exact lifecycle callback obligation is actively executing, Core rejects any reentrant attach, detach, or structural operation whose committed result would cause a true inverse ownership transition of that same subject. An attach-phase callback cannot directly detach the subject or indirectly remove its final anchor/membership, and a detach-phase callback cannot directly attach the subject or indirectly add the first anchor/membership. Core evaluates the prospective result through the exact committed overlay and throws ordinary `InvalidOperationException` before the nested backing writer, ledger mutation, route/state publication, lifecycle callback, Registry/parent projection, or other nested ownership effect. It does not adopt, suppress, or replace any original callback obligation.

This rejection is an explicit programming-contract rule, not contention, unfinished state, stale-state retry, or internal control flow. The same exact inverse call made again while the same callback obligation is active fails identically against the same committed state. A call made after that callback and its original reconciliation complete has different lifecycle preconditions and may succeed normally. If callback code catches the exception, the original reconciliation simply continues. If it escapes the callback, built-in Tracking has already marked that callback attempted/delivered, captures the exception as that callback's EDI, completes every remaining original callback and mandatory baseline/route/Registry/parent/finalization obligation, and then rethrows it under the existing first-EDI precedence. The original attach or detach reaches its normal quiescent committed result in either case.

Supported nesting remains broad. Topology-bearing work on another subject, same-subject structural or metadata work that does not cause the true inverse transition, and same-subject source changes governed by the route-only matrix continue through the overlay protocol. Scalar/read/invoke/service operations remain outside this rejection. The rule is keyed by the exact currently executing lifecycle callback obligation and exact subject, not by thread, domain, or a broad ban on reentrancy.

## Context Mutation and Array Pinning

`AddService`, `TryAddService`, `AddFallbackContext`, and `RemoveFallbackContext` enter the topology gate before `_mutationLock`. Each operation materializes or invokes its application input exactly once. `TryAddService` keeps current behavior: it checks services in order, invokes `exists` once per examined service until a match, calls `factory` at most once, rereads source state after callback reentrancy, and publishes one replacement state. Internal restart never replays either delegate.

These context mutation APIs run the settlement barrier before authority analysis or action selection when called under an ancestor committed-pending segment. When called reentrantly from an ancestor already in `Reconciling`, they use its exact committed-but-unpublished overlay for affected-domain authority and action selection without resettling it. The exact same once-only predicate, factory, and materialization rules apply in either case. Ownership queries use the settled state or active exact overlay as appropriate; ordinary lock-free service resolution retains the phase-appropriate immutable last-published-state behavior above.

A predicate or factory may mutate the same or another built-in context synchronously. Nested context work reenters the topology gate and takes only its target `_mutationLock`. A simultaneous reverse external caller waits outside all context locks. Custom `IInterceptorSubjectContext` implementations remain responsible for their own synchronization.

Before immutable publication Core substitutes the prospective state into the reverse dependency walk and computes the exact lifecycle coordinator identity set of every affected active ownership domain using `ReferenceEquals` only. Publication is legal only when each set remains the same zero-or-one reference identity. A change from none to one, one to none, one instance to another, or one to two on an active domain throws `InvalidOperationException` before context state and reverse edges publish, including when distinct instances are `Equals`-equal. This is permanent semantic incompatibility. Nonunique service additions and fallback composition remain legal.

This authority check uses the existing context reverse-dependency cone and active-domain identities. It does not enumerate subject roots, clone an ownership ledger, or rebuild Tracking's outgoing structural baseline. An identity-preserving context mutation changes immutable context state for future operations while every active structural operation continues its already pinned interceptor and handler arrays. If publication occurs during `Reconciling`, the same reverse cone also invalidates and clears affected committed-but-unpublished overlay arrays/chains as specified above; a later nested topology prefix or action rebuilds those inputs lazily against the exact new contributing `ContextState` identities.

One structural operation pins:

- the exact cached `WriteInterceptorChain<TProperty>` and its immutable interceptor array after topology-gate entry and before the prefix;
- for every affected subject, one exact reference-identity-deduplicated prospective `ImmutableArray<ILifecycleHandler>` resolved during preparation against the then-current executor snapshot plus proposed route overlay, and the exact index whose element is `ReferenceEquals` to the supported Tracking coordinator, dividing its pre-coordinator and post-coordinator segments;
- for every affected subject and property phase, one exact cached `ImmutableArray<IPropertyLifecycleHandler>`;
- the exact Core-issued current route identity, subject generation, proposed route target, and ownership-domain identity used by those snapshots. Core alone retains the internal current/expected descriptors needed for publication; no facade view exposes them.

For attach, the prospective lifecycle and property arrays are resolved without prebuilding a routed `ContextState`. For detach/final release, current arrays come from the exact current old immutable state. The same pinned lifecycle array supplies both segments around the coordinator, preserving the current ordered service set. The supported official Tracking `ILifecycleInterceptor` must appear in that array as the exact same object reference through its `ILifecycleHandler` role. Tracking scans the immutable array with `ReferenceEquals`; that one index is the logical coordinator slot. If no exact slot exists, Core rejects before any backing, ownership, metadata, or context commit with persistent `InvalidOperationException`. The built-in `LifecycleInterceptor` remains at the exact former `ContextInheritanceHandler` ordered position. Every descendant is pinned during preparation, not lazily during callback descent. Pooled `LifecycleReconciliationState` entries retain immutable array structs and the coordinator index without copying arrays.

The exact official Tracking coordinator occupies one logical ordered coordinator slot. Its advanced reconcile/coordinator phase replaces its ordinary `HandleLifecycleChange` callback at that same array index for the same lifecycle change; it is not invoked in both roles. Reference-identical repeats of that coordinator across service paths collapse to the first ordered occurrence before the scan and do not duplicate the slot. Distinct noncoordinator handler instances remain distinct even when `Equals` says equal; repeated discovery of the same exact noncoordinator instance collapses by reference identity. An official coordinator needing an additional ordinary callback registers a separate handler object.

A legal handler callback may add a nonunique handler or identity-preserving fallback. During a property-carried transition this may occur before coordinator-slot route publication, which merges the then-current immutable executor state as described below. During explicit-root attach the configured-context route is already published before phase 1; identity-preserving mutation updates the current immutable state and invalidates dependents normally but does not republish or replace the exact route descriptor. In either entry mode the current operation continues its already pinned arrays for every later subject and property phase. A synchronously nested new operation pins the newly published arrays and may observe the addition. On return, the outer operation resumes its old arrays.

For a property-carried first attach, property-carried final release, or route-only selected-parent transfer, `TryPublishCommittedRoute` remains the exact coordinator-slot capability. At that phase it rereads the then-current immutable executor state, materializes any fresh `ContextOwnershipRoute`, and merges it into a fresh routed `ContextState` preserving all legal earlier service/fallback mutations. Semantic compatibility and required mutable buffer capacity were validated before backing commit, so this phase cannot introduce a semantic rejection. An out-of-memory failure is outside recoverable semantic guarantees. Before construction, Core verifies that this exact publication obligation remains `Pending` and that its expected route-identity dependency is still valid. A nested later generation with the same identity or a net-zero/unrelated change does not make the publication disappear. A nested operation that invalidates it must first supersede/adopt it and own the correct serial replacement, after which the older publication returns `false` with a default result without constructing anything. On successful publication Core returns the exact resulting identity: the old identity when the internal descriptor remains exact, and a different identity for every changed descriptor even when its target compares equal. Property-carried route objects are therefore constructed only after the final exact obligation/identity guard. Prospective service-walk/handler arrays are the unavoidable earlier exception: they must be pinned before any user callback to preserve callback order, so a callback-created later generation can supersede an outer property-carried route publication after those arrays were already materialized. The route-changing allocation rows count that case separately.

Explicit-root route transition is not a provider-selected coordinator-slot capability. On true explicit-root first attach, Core performs the same final validation, exact descriptor/identity assignment, immutable-state merge, reverse registration, and route publication immediately after ledger commit and before root lifecycle phase 1. Every root attach callback therefore resolves through the new configured-context route, including pre-coordinator service handlers. The logical coordinator phase performs descendant reconciliation but does not republish the root route. On true explicit-root final detach, Core commits the anchor/final-release ledger delta but retains the exact old immutable route through all root lifecycle phases 1 through 6. Only after the complete root callback cursor is delivered or exactly adopted does Core perform the guarded route clear, unregister, and reverse invalidation, then marks that root release complete. Every delivered root detach callback therefore resolves the old route. These explicit-root publications use the same exact generation/route-identity obligation and later-operation adoption guards but are invoked directly by Core at their fixed outer boundaries rather than through `TryPublishCommittedRoute`.

Every planned callback or publication phase carries an exact internal obligation token with the subject generation, expected opaque route identity, and state `Pending`, `Delivered`, or `Superseded/Adopted by exact later operation`. A descendant phase captures through `SubjectOwnershipView` the exact selected-parent subject route identity on which its route and callback meaning rely. Tracking applies the committed baseline before dispatch. Immediately before invoking a callback, Tracking changes its exact obligation from `Pending` to `Delivered`; for callbacks, `Delivered` means attempted exactly once whether the callback returns or throws, and reentrancy cannot replay it. A successful publication likewise changes its exact phase to `Delivered`. A later raw subject generation or false current guard never silently discards an obligation.

Before a synchronously nested later operation returns or rethrows after commit, it classifies every still-pending obligation in the affected linked ancestor frames. A semantically valid same-route-identity, net-zero, or unrelated obligation remains `Pending` in the older pinned tail and continues after the nested call even when its recorded generation is older. For a supported nested operation that is not rejected by the active same-subject inverse rule, an obligation made obsolete by true detach or by a changed selected-parent/route identity becomes `Superseded/Adopted` only when the exact later operation owns the replacement callback or publication required by the valid serial history. The later operation delivers that replacement exactly once. Independent siblings continue in the older tail, and a descendant is adopted only when its captured selected-parent subject route identity no longer matches the exact committed dependency. A failed precommit nested operation, including the stable same-subject inverse rejection, changes no obligation state. Thus an obsolete action is suppressed only with an exact replacement/adoption, and no callback or publication disappears merely because generation or route-identity comparison noticed newer state.

Obligation state and exact adoption links live inline only in affected entries of the pooled reconciliation frame and its synchronously linked nested frames. They create no persistent per-subject object, managed allocation, stable-write branch, or route-free allocation. Frames clear tokens, generation/route-identity dependencies, and links after delivery, adoption, cancellation, or final release. Guard checks run only for affected reconciliation phases.

An active initiating structural interceptor prefix that synchronously attaches or detaches its own subject cannot splice the already selected structural chain and cannot replay the prefix, whether that subject is route-free or already owned. A route-free structural prefix likewise cannot change the coordinator identity selecting its own chain. Core detects that exact structural-operation self-modification and throws ordinary `InvalidOperationException` before publication. The same structural prefix, arguments, and committed state fail identically on immediate retry. External topology callers wait for the structural prefix/topology turn to finish and then succeed according to the resulting committed state. Coordinator-preserving nonunique mutation remains legal and affects future operations. Scalar prefixes remain outside the topology gate and carry no active-prefix marker: they may synchronously attach or detach their own subject, their already selected scalar chain completes, and future operations observe the new route. External scalar/ownership interleaving retains current serializable visibility.

## Ownership State Machine

Configured-context activation is:

```text
Absent -> Preparing -> Active -> Releasing -> Absent
          |                         |
          +---- failure cleanup ----+
```

The activation stores domain identity, exact coordinator identity, generation, lease count, and reverse affected-domain membership. It is state, not a monitor. Failed first activation clears every binding and reference before returning to `Absent`.

Each one-shot ledger-bearing `ExplicitAttach`, `ExplicitDetach`, or `MetadataAddition` batch follows:

```text
Preparing -> Committed -> Reconciling -> Finalized
Preparing -> Cancelled -> Finalized
```

There is no `Committing` public or internal phase and no second publication monitor. The topology gate covers validation, direct store, ledger publication, segment settlement, and final invocation release. A pooled `StructuralPrefixScope` is a non-ledger carrier for exact active-prefix identity and invocation nesting; it is pushed before the structural chain and returned in `finally`, while scalar chains allocate/push nothing. Each structural coordinator invocation instead pushes one ledger-bearing child accumulator with one exact invocation identity and may contain several settlement segments. A cancelled structural attempt is cleared and restarted at its terminal boundary without becoming a public transition, failure, provider release, or callback boundary.

Within that invocation, each exact segment follows:

```text
Empty -> PreparingAttempt -> CommittedPending -> Reconciling -> Settled
                       ^          |
                       +----------+  later ordinary terminal attempt before settlement
```

`PreparingAttempt` is tentative. A successful terminal commits backing storage and the Core incoming-ledger generation, clears attempt-only reservations, and enters `CommittedPending`; Tracking baseline, lifecycle callbacks, route publication, and route finalization remain deferred. A later ordinary downstream terminal before nested topology work creates a new tentative revision over the same segment, diffs from the committed overlay, and replaces `CommittedPending` on success. A segment retains its exact segment-start Tracking baseline, route target, generation, and opaque route identity separately from every intermediate overlay; Core alone retains the corresponding internal descriptor where one exists. When the segment settles, Core exposes one net delta from that start state to the last successful overlay. Tracking completes the entire reconciliation cursor and every mandatory consistency action before a callback exception may escape `ReconcileSubjectOwnership`, so `Reconciling` reaches its logical settled outcome even on that exceptional return. A later terminal after `Settled` starts a new segment epoch in the same coordinator invocation. Core may therefore invoke `ReconcileSubjectOwnership` several times for one invocation but invokes `ReleaseSubjectOwnership` once.

Every state-machine transition that needs a next ownership generation, route-free epoch, invocation identity, or segment identity first completes the checked reservation protocol above. Exhaustion leaves the current state, backing storage, ledger, Tracking baseline, route, metadata, Registry projection, callbacks, and pending obligations unchanged for that rejected action. Attempt cancellation and stale-snapshot restart reuse the still-current invocation/segment identities and therefore do not consume identities merely because library-controlled discovery restarted.

A nested structural or metadata operation that finds any target subject reserved by an outer `PreparingAttempt` cancels every tentative reservation in that attempt before selecting its own action. `IsPreparationCancelled` becomes true for that operation view, and Tracking returns without further application traversal. If the invocation has an earlier successful overlay, cancellation restores its `CommittedPending` state and the mandatory barrier settles it before the nested action. With no earlier successful overlay, the nested operation executes independently from current committed or route-free ownership. After it completes, the outer Core terminal boundary repeats discovery from final values in a new segment when the nested operation created a topology-visible serial boundary. It never replays the interceptor prefix, a backing writer that already ran, lifecycle callback, `TryAddService` predicate/factory, or `AddProperties` input enumeration. A stale tentative topology snapshot with no topology-visible nested operation may restart within the same segment epoch and likewise never exposes a public retry.

Restart is unbounded for library-controlled cancellation, reentrant committed structural change, or stale topology snapshot. There is no cancellation counter, finite retry exception, or public retry result. Application structural traversal that mutates finitely many times and stabilizes must succeed regardless of whether stabilization occurs before or after any former numeric threshold. Traversal that changes relevant application state on every pass may prevent the synchronous call from returning; that is an unsupported application liveness/programming-contract condition, not a library-thrown failure.

A nested topology-bearing operation during `Reconciling` selects its action and interceptor/handler inputs from the exact committed-but-unpublished overlay before invoking a prefix, creates a later generation when it commits, and is the valid serial winner for the state it actually changes. Before returning or rethrowing after commit, it classifies the linked ancestor's pending obligations. Same-route, net-zero, and unrelated phases remain owed by the older pinned tail; only phases invalidated and exactly adopted by the later operation stop there. The older tail never clears or reports later state, never loses an obligation from raw generation change, and the barrier never reenters settlement for the same reconciling segment. Ordinary `GetServices` continues to report the ancestor phase's publicly visible route throughout this selection.

## Incremental Ownership Planner

The final PR #419 planner is incremental. The current implementation's whole-root current/prospective graph reconstruction and cloned operation ledger are prohibited architecture, not an optimization left for later work. Normal structural admission derives its result from the initiating relationship delta, newly reached route-free subtrees, and, only when release is possible, the affected forward component. Its work and temporary storage are independent of unrelated explicit roots and owned components. Beyond the capability-minimal public facade specified in this design, this internal planning architecture changes no ownership result, callback order or visibility, generation/route-identity rule, stable error outcome, or external benchmark contract.

### Authoritative committed indexes

Core owns the only authoritative incoming ownership ledger. Each subject entry contains its explicit anchor, exact ownership domain and coordinator, generation, selected parent and route, and incoming parent memberships keyed by exact `PropertyReference` in insertion order. The subject executor separately owns the exact committed metadata publication snapshot exposed by `SubjectOwnershipView`; it is metadata order, not a second ownership truth. The first incoming membership is inline and overflow is allocated only when required. No provider-owned attached-subject set, synthetic root set, reachability snapshot, or second membership truth may be retained.

Tracking owns the committed outgoing structural baseline needed to diff later values and project callbacks. It is indexed first by subject identity and then by exact property identity. It retains the exact committed structural value references required by the `O(1)` identity fast path without prescribing a dedicated field or storage layout. Each property entry retains unique children in first-occurrence order, reference-identity lookup, and the first committed occurrence metadata needed by projections. The baseline is not proof that a subject is attached. Core's incoming ledger decides ownership, route selection, and release. Tracking applies an exposed committed operation to this baseline before invoking its callbacks and removes released subjects and properties during the same reconciliation turn.

The two indexes are complementary rather than duplicated. Core can enumerate a subject's exact surviving incoming memberships through `SubjectOwnershipView`; Tracking can enumerate a subject's exact outgoing property entries directly without scanning all properties in the domain. No terminal clones the incoming ledger, outgoing baseline, explicit roots, or all reached subjects. Tentative and coalesced values live only in the exact operation frame.

### Local property diff and committed overlay

Each structural terminal starts from the initiating property's current committed Tracking entry, or from the current segment's most recent successful overlay when downstream has already stored without an intervening settlement barrier. The proposed direct value is visited once in occurrence enumeration order. Reference-identity lookup deduplicates Core membership while retaining the first proposed index or key for property projection. A retained child may update first-occurrence metadata without removing and re-adding its Core membership. Integer indices remain unboxed in an internal discriminated occurrence representation; conversion to `object` is permitted only when constructing an actual callback whose public contract requires it.

Arbitrary collection and dictionary values remain supported. Arrays and `IList` take the library's allocation-free indexed fast paths and are the authoritative zero-allocation protocol and benchmark shapes. `IDictionary` retains dictionary-specific handling and every arbitrary supplied dictionary remains valid, but its enumeration shape is not universally allocation-free. A supplied container exposed only through an arbitrary `IEnumerable`, or any dictionary whose usable traversal is its supplied enumerator, preserves that enumerator's exact occurrence order. Any allocation or boxing performed by a supplied collection or dictionary enumerator is configured supplied-container/application work, not library ownership-protocol allocation. The planner itself still stores integer positions and dictionary occurrence metadata unboxed until an actual public callback requires `object`. PR #419 adds no typed enumerator facade and does not restrict collection or dictionary capability to obtain a benchmark result.

When the proposed value is the exact committed value object, direct mutation outside the gated setter remains unsupported, and no earlier terminal overlay supersedes that baseline, the planner takes an `O(1)` reference-identity fast path. Otherwise the diff records added, removed, retained, and first-occurrence-changed children in expected `O(old + new)` time. Each Tracking property entry keeps its committed unique children in one compact array whose ordinals remain stable until settlement. Zero and one child bypass dense scratch storage. A first nontrivial diff lazily creates or reuses property-owned bank 0, whose dense cells are indexed by those stable committed ordinals. If a later downstream tentative revision must coexist with a committed-pending overlay, and only then, the property lazily creates or reuses bank 1. A successful terminal swaps the tentative bank into the committed-pending role and clears the previously active bank; cancellation or supersession clears the tentative bank and preserves the committed-pending bank. A later revision alternates the two roles. There is no third bank.

Children introduced only by the current overlay have no committed ordinal and therefore use frame-local inline-first provisional entries until settlement. Settlement first consumes the final committed-pending bank and provisional entries into the persistent Tracking baseline, then clears both banks and every provisional reference before callbacks or a nested topology action can run. The compact committed child array may then be rebuilt or resized and its new ordinals remain stable until the next settlement. The banks are nonsemantic scratch, never a second attached-subject or committed-membership truth. All object and key references are cleared on cancellation, supersession, and settlement. A semantic visit token never silently wraps; at its maximum it may reset only after one complete synchronous sweep clears both dense banks and every associated object/key reference, so no stale cell can become current.

One coordinator invocation owns one accumulator with one committed overlay per uninterrupted segment. After each successful downstream terminal store and Core ledger commit, that terminal replaces the current segment overlay for the initiating property and its final committed delta. A later ordinary terminal diffs against that overlay rather than the persistent baseline. Cancellation clears only the currently tentative revision and preserves any earlier successful overlay. Settlement applies only the segment's final coalesced overlay to Tracking's persistent baseline before callbacks, then marks that segment settled. An upstream repeated continuation creates a separate coordinator invocation; a supported nested topology operation settles the nearest pending segment and a later downstream terminal starts a new segment in the same invocation.

For `A -> null -> A` or `A -> B -> A` with no intervening nested topology, settlement compares the final overlay with the segment-start baseline and emits no lifecycle callback or route publication for a net-zero ownership delta. Core ownership generations may have advanced for successful stores, but the segment-start exact route descriptor and opaque identity survive. The Core accumulator retains the descriptor while the provider frame retains only the identity, each independently of intermediate targets; target equality is never used to reconstruct or replace either. If nested topology work is requested while `null` or `B` is pending, the barrier first settles that intermediate state. A later restoration to `A` is a new segment and may require a fresh route descriptor, a different route identity, and the ordinary callbacks for its actual serial transition.

An atomic `AddProperties` batch uses the same frame and indexing rules across every newly added direct-readable structural property. The once-materialized metadata/value slots are its local initiating set, and all property deltas, newly reached subtrees, and reservations commit or cancel together. It does not clone unrelated outgoing entries or scan an already owned root merely because metadata changed.

### Addition, validation, and selected-route retention

Canonical discovery order is part of ownership semantics. An executor captures and retains one exact committed metadata publication snapshot independently of its public metadata dictionary. Generated subject `Properties` enumeration is the generator's declaration order; derived/base composition preserves the base metadata prefix and appends the derived declarations in generated order. Dynamic materializes its initial input once and its `Properties` enumeration returns that exact materialization order independently of the lookup representation. On the first topology operation, Core captures that generated or Dynamic ordered enumeration exactly once under `OwnershipTopologyGate`. For a manual subject, Core likewise enumerates its initial `Properties` exactly once under the topology turn and that supplied enumeration becomes its publication order. Subsequent metadata mutation for every subject shape is supported only through `AddProperties`. Each successful atomic `AddProperties` batch appends its once-materialized input order atomically, while rejection or cancellation appends nothing.

Official Tracking traverses `SubjectOwnershipView` by `PropertyCount` and `GetProperty(index)` and never enumerates `IInterceptorSubject.Properties`, `IReadOnlyDictionary`, or a frozen dictionary for lifecycle discovery. Within one structural property, scalar subject values contribute one occurrence and collections or dictionaries contribute occurrences in their direct enumeration order. Tracking performs recursive-equivalent depth-first discovery: mark a route-free subject visited before descending, visit its readable structural properties in the view's committed metadata order, and for each occurrence reserve the membership and immediately descend the first newly reached route-free child before continuing to the next occurrence.

For each directly or recursively added child, Tracking first asks Core to validate and reserve the exact incoming membership. The first encountered parent of a route-free subject becomes its selected parent before descent. A later back edge, cross edge, or DAG join to a subject already visited in this preparation adds the exact membership but neither reselects nor traverses it. A subject already committed in the same exact ownership domain and coordinator is likewise compatible: the planner adds its new incoming membership, retains its committed selected parent, and stops because its outgoing baseline is already indexed. An owned subject from another domain or coordinator rejects before the backing store. This mark-before-descend rule closes cycles and makes same-batch DAG selection deterministic without recursion-dependent duplication.

Discovery validates the complete newly reached route-free subtree before commit and pins callbacks only for subjects it affects. It never walks through a compatible already-owned subject to rediscover its descendants. Within an atomic relationship delta, all removals are planned and reconciled before additions. A direct scalar property contributes at most one removal and one addition. A direct collection or dictionary property scans the prior committed old-occurrence stream in reverse; the first reverse encounter of each absent reference-identical child emits its one membership removal and carries that exact old occurrence, while later reverse encounters of the repeated child emit nothing. This is master's reverse prior committed unique-child/old-occurrence removal order, including the last old occurrence for a repeated child. Additions scan proposed occurrences forward; the first forward encounter of each new reference-identical child emits its one addition and carries that occurrence before canonical descendant discovery. An old child is therefore completely detached before its replacement is attached. The cost of an addition is the local old/new property diff plus newly reached subjects and edges, independent of already indexed compatible descendants and unrelated roots.

An explicit anchor remains selected while present. Otherwise the current selected incoming parent remains selected when that exact membership survives and remains acyclic. Removing or adding a nonselected compatible membership does not churn route selection. Only loss or invalidation of the selected relationship invokes insertion-order fallback among surviving compatible acyclic memberships, where insertion order is the canonical reservation order above. Ownership route transfer occurs only when the selected relationship or route target actually changes. First publication and PR #474 context-state invalidation retain their existing rules. The exact generation, opaque route-identity, obligation-adoption, and stale-no-op rules remain unchanged; internal descriptor equality preserves identity, while an internal descriptor change always changes identity.

### Affected-component release

Removal of a nonselected incoming membership cannot release a child whose explicit anchor or selected incoming relationship still survives, so it performs only the local membership and projection delta. Removal of an explicit anchor or selected incoming membership is the only normal trigger for an affected-component release scan.

For such a trigger, the planner builds `C`, the forward closure from the potentially released subject or subjects through the prospective outgoing baseline, including the initiating-property or metadata-batch overlay. It seeds `live` with every subject in `C` that retains an explicit anchor or has a surviving prospective incoming membership from a subject outside `C`, then follows prospective outgoing edges from those seeds within `C`. The final-release set `R = C - live` is the exact release set. Core removes incoming memberships whose parents are released and reserves final release for every subject in `R`. This releases an orphaned cycle, preserves a shared descendant reached from a live seed, and handles a new outside edge in the same operation in expected `O(C + EC)` time. It never inspects an unrelated root or component.

Before reconciliation, the planner classifies one selected-final-carrier forest over `R`. Candidate roots retain the exact initiating removal stream order: scalar removal contributes at most one root, direct collection/dictionary removal scans prior committed occurrences in reverse with reference-identity unique-child suppression as defined above, and an exact explicit-root detach contributes its one root entry. The planner takes the next still-unplanned candidate as the next forest root and completes that root's planning before considering the following candidate; a later candidate already planned through an earlier tree does not start another tree, and its initiating edge is nonselected for that destination. From each first encountered subject in `R`, descendant planning enumerates that subject's committed metadata in publication order and each committed structural property's occurrences in forward occurrence order; the first forward occurrence carries that exact `PropertyReference` membership, while later occurrences of the same reference-identical child in the same property are duplicate occurrences and emit no additional edge or callback. The first encountered membership edge to an unplanned destination selects that destination's final carrier and marks it `ReleasePlanned` before examining its descendants. This selected-final-carrier role is determined solely by first encounter in the release forest and need not be the destination's prior active selected membership. If that prior selected edge is encountered later in `R`, it is a noncarrier, as is every later distinct back, cross, or DAG membership edge to a `ReleasePlanned` destination, and it retains its planning encounter order relative to the other nonselected edges for that destination. Planning completes the affected forest before callback dispatch, so every nonselected incoming membership is emitted in that encounter order as its ordinary nonfinal removal immediately before the destination's selected final carrier. Planned callback `ReferenceCount` is the remaining committed property-membership count after that removal, not total lifetime-source count. A noncarrier reports a positive value only while another property membership remains; it may report zero when an explicit anchor alone keeps the subject live, in which case `IsContextDetach` is `false`, no final carrier/release callback runs, and the explicit route remains selected. A selected final carrier in `R` reports zero with `IsContextDetach` true. The chosen carrier is therefore the one final property-carried removal only when no explicit anchor or other live seed survives, even for cycles and DAG joins, and no old-generation membership callback remains after that subject completes final detach. Later exact removal of a surviving explicit anchor is its own true final-detach operation.

The release walker uses one iterative thread-static pooled cursor for the complete forest. One cursor entry retains only the affected-subject/selected-carrier indexes, next committed metadata and occurrence indexes, and an entry mode for nonselected incoming removals, property-carried prefix, descendant traversal, property-carried route-clear/post suffix, explicit-root-after-descendants, explicit-root full phases, explicit-root post-phase-6 route clear, or completion. It does not use CLR recursion, a cloned graph/release snapshot, separate pre-order and post-order arrays, or a per-subject callback list. The cursor transitions each subject `ReleasePlanned -> ReleaseEntered -> ReleaseCompleted`, setting `ReleaseEntered` before any prefix or descendant action. An already entered or completed destination is never pushed again. Pooled affected entries hold the forest links, marks, pinned arrays, and exact obligation tokens; warmed retained capacity makes traversal allocation-free.

A property-carried final release is split around the exact coordinator slot. Its prefix runs in pre-order: all property detach phases in committed metadata order, `SubjectDetaching` event subscribers, the subject lifecycle handler, and current lifecycle service handlers before the coordinator. At the coordinator, the same cursor removes or releases descendants in committed metadata and forward occurrence order, completing a selected final-carrier child recursively-equivalently before advancing, while a boundary edge to `live` emits only its ordinary nonfinal removal and any required callback-silent selected-parent transfer. For a destination in `R`, Core publishes no transient selected-parent transfer when its first-encounter carrier differs from its prior active selected membership. The exact old public route remains visible until the first-encounter carrier performs the one final clear, while nested topology during this committed-but-unpublished interval selects from the exact committed route-free overlay. After every descendant is complete, Core clears the subject's final route and Tracking invokes the current post-coordinator service suffix in post-order, then marks the subject `ReleaseCompleted`.

An exact explicit-root detach is the deliberate special entry that preserves master. The cursor completes every descendant tree first in committed metadata and forward occurrence order, then runs the root's full ordinary detach sequence with no descendant work left: root property phases, `SubjectDetaching` event subscribers, subject handler, pre-coordinator services, the coordinator phase without root route clearing, and post-coordinator services. The exact old root route remains published and visible through the last post-coordinator callback. After phase 6 finishes, Core executes the root's guarded route clear and reverse invalidation and only then marks `ReleaseCompleted`. When the initiating stream contains several release roots, the cursor completes one selected-carrier tree, including its post-callback route clear, before entering the next root. A cross-root or DAG edge already classified as nonselected is removed before its destination's final carrier and does not create a second final-detach tree. No callback belonging to a subject's completed final-detach generation runs after `ReleaseCompleted`; a later independent true attach belongs to a new generation.

Every cursor callback, nonfinal removal, property-carried coordinator-slot route clear, explicit-root post-phase-6 route clear, and suffix retains its exact generation/opaque route-identity obligation token. The release marks are traversal state, not a substitute for owed-phase adoption. A nested later operation leaves still-valid obligations on the older cursor, or explicitly adopts and replaces only invalidated obligations before returning; raw generation change never skips a release phase. Tracking marks each callback delivered before invoking it, continues the cursor across callback exceptions and across later roots, and marks `ReleaseCompleted` only after every phase and the entry-mode-specific route clear are delivered or exactly adopted. The first callback EDI escapes only after the complete release cursor and mandatory consistency work finish, while Core finalization/release retains the established exception precedence.

Affected subjects are direct membership additions/removals, first-attached subjects in newly reached subtrees, final-detached subjects in `R`, selected-route transfers, and a property owner whose retained occurrence projection changes. Only subjects with actual callback work pin current removal arrays, prospective addition arrays, property arrays, generations, opaque subject/selected-parent route identities, and inline owed-phase state; a callback-silent route-source transfer pins only its exact route-identity/generation publication obligation. Core retains any internal descriptor needed to perform that publication. Dispatch remains linear in the affected set, processes every removal before any addition, detaches an old child completely before attaching its replacement, and invokes each required phase once per settled segment. Property-carried routes publish or clear only at the exact coordinator boundary; explicit-root first attach publishes before root phase 1 and explicit-root final detach clears after root phase 6. No ordinary one-context callback order, visibility, route-selection result, generation rule, or owed-phase adoption rule changes.

### Frames, lookup, and retention

Every Core structural prefix scope and coordinator accumulator owns a distinct LIFO pooled carrier. Every Tracking coordinator invocation owns a distinct LIFO frame identified by its exact Core-issued invocation identity. That provider frame retains the current segment identity, segment-start baseline and opaque route identity, committed-pending overlay, publication guards, and tentative revision separately; it never retains an internal route descriptor. Core's paired accumulator alone retains a segment-start descriptor when routed. Ordinary downstream repeats reuse the segment storage until settlement; a later segment clears and reuses only its settled segment storage. A synchronously nested coordinator invocation has a different invocation identity and rents another Core accumulator and Tracking frame even while an outer frame is preparing or reconciling. Cancelling an outer tentative attempt clears only that revision's reservations, pending visit tokens, and proposed values; it cannot clear, reuse, or roll back a nested frame, either segment-start identity/descriptor, or an earlier successful committed-pending overlay.

Affected entries, direct child entries, memberships, traversal work, and overlay-only child entries use inline-first storage. Reference-identity dictionaries and executor-to-entry indexes are created lazily only after the inline threshold and are retained in thread-static pools. Core clears every internal exact descriptor before returning its accumulator. Core and Tracking clear every subject, property, key, segment-start value, committed overlay, opaque identity, handler array, previous-frame link, and other application reference before returning a frame or buffer. Retained operation-list capacity and operation set/dictionary capacity-equivalent are capped at 1024. Storage exceeding 1024 is cleared and dropped instead of being retained by an operation pool.

The two dense scratch banks are property-owned storage rather than operation-pool buffers. A bank larger than 1024 may remain with that property only while its committed topology remains large and stable, which preserves the warmed zero-allocation row. Topology shrink clears and drops or resizes excess bank capacity; property removal and final subject release clear and drop both banks. No nested frame borrows an active bank: the mandatory settlement barrier clears both banks before nested topology selects an action, after which the nested invocation uses its distinct frame and the now-free property banks.

The normative asymptotic bounds, excluding configured application/interceptor work and immutable route publication costs, are:

| Operation | Required planner cost |
|---|---:|
| same committed value reference with no superseding overlay | `O(1)` |
| new collection or dictionary value, including arbitrary fallback enumeration | expected `O(old + new)` protocol work plus supplied-container enumeration cost |
| add or replace | expected `O(old + new + newly reached subjects + newly reached edges)` plus a release scan only when a removed selected relationship can release a component |
| remove an anchor or selected incoming membership | expected `O(old + new + C + EC)` |
| nonselected membership removal | expected `O(old + new)` |
| local write in a graph with unrelated owned roots/components | independent of unrelated graph size |

After warming retained capacity and persistent indexes, same-reference and same-membership structural rows allocate zero managed bytes beyond configured application work. A membership change may allocate new persistent Core/Tracking entries or overflow capacity, and an actual route change may allocate only the immutable and reverse-publication costs listed in Performance Acceptance. It must not allocate a whole-graph snapshot, cloned ledger, fresh operation frame, boxed index, or unrelated callback/service array.

## Structural Write Protocol

Task 1's retained `CanContainSubjects` classification selects the path. Scalar properties use the existing public four-argument executor API and never enter the topology gate. A zero-interceptor read remains lock-free; an intercepted read terminal and scalar write terminal acquire the private executor monitor. Structural properties use:

```csharp
bool SetPropertyValue<TProperty>(
    string propertyName,
    TProperty newValue,
    TProperty currentValue,
    Action<IInterceptorSubject, TProperty> writeValue,
    bool canContainSubjects);
```

The existing per-executor `Revision` remains the legacy commit-order label assigned by the write terminal and consumed by Tracking and connectors. PR #419 preserves its existing scalar and structural increment, write-context propagation, and hot-path shape. Ownership preparation, admission, ABA protection, validation, and retry do not capture, compare, or recheck that value, and the checked ownership-identity exhaustion contract does not apply to it. No ownership frame stores an initiating or expected executor `Revision`; no new structural stamp, executor field, or per-property mutation counter is introduced. An ownership frame may pass the already assigned post-commit label onward for existing Tracking/connector behavior, but may not use it to authorize or reject an ownership action.

The caller-supplied `currentValue` is likewise not ownership authority. It is the existing value captured before executor entry and remains available to the ordinary interceptor context, so it can be stale when a structural call waits for topology admission. After admission, Tracking plans from its exact committed structural baseline, or the current segment's committed-pending overlay, and the synchronous direct writer overwrites backing storage in topology-turn order. Two valid structural writers therefore produce two serial baseline deltas even when both calls captured the same earlier `currentValue`.

Generated, Dynamic, and compliant manual structural setters use this overload, and `AddProperties` uses its gated metadata protocol. A direct structural storage mutation through the four-argument scalar overload, an incorrectly classified manual setter, or another custom bypass violates the direct-storage/gated-setter contract. Such a bypass is application/provider misuse and receives no ownership consistency, ABA, or deadlock guarantee.

If the subject has no active exact lifecycle coordinator, the structural overload preserves ordinary write-interceptor behavior but creates no ownership batch, parent membership, baseline, child route, or lifecycle callback. Explicit ownership of the root remains intact. This applies both to a prepopulated child at explicit attach and a child assigned later. If the supported official coordinator installed by `WithLifecycle()` resolves as exactly one `ILifecycleInterceptor` reference and appears as the reference-identical element in the `ILifecycleHandler` array, it receives the protocol. Two distinct coordinator references are incompatible even when value-equal; a missing exact handler slot is invalid configuration.

With the exact lifecycle coordinator, continuation behavior remains position-dependent exactly as in the current chain. A repeating interceptor upstream of the coordinator invokes the coordinator independently for each `next`; every coordinator invocation owns a different identity, settles any committed segment, and releases before the upstream repeater can call `next` again. A repeating interceptor downstream of the coordinator executes zero, one, or several terminal attempts inside one coordinator invocation. With no supported nested topology operation between those attempts, they remain one uninterrupted segment: zero successful stores produce no reconciliation, while one or several produce one coalesced reconciliation after downstream returns from the segment-start Tracking baseline to the final successfully stored value. The prefix before the repeater is never replayed.

The coordinator-invocation accumulator records ordered terminal-attempt metadata and the most recent successfully committed Core ownership generation/delta per segment. It is not a callback queue. Each terminal attempt independently uses the exact committed Tracking baseline or current segment overlay, prepares and validates its proposed value before its direct backing store, commits its Core incoming-ledger generation after a successful store, and then replaces the segment's committed-pending delta while clearing superseded tentative buffers. Intermediate downstream stores do not emit lifecycle callbacks or route publication. A supported nested topology call ends that coalescing interval: the barrier settles the nearest committed-pending segment, and a later downstream terminal uses a new segment identity and rebases from the now-published Tracking baseline and opaque route identity while Core retains the internal descriptor. A nested operation during barrier callbacks is a later generation; it leaves valid older obligations pending and stops a dependent action only through exact supersession/adoption by the later operation.

If a later terminal attempt is permanently incompatible, it rejects before its store, the earlier committed-pending segment settles during unwind, and the incompatibility remains the primary exception. If the direct writer throws before mutation, Core cancels that attempt, settles any earlier committed-pending segment, and preserves the writer exception. If downstream throws after one or more successful stores, Core settles the final pending segment and finalizes the invocation before the original downstream exception wins. This preserves current `LifecycleInterceptor` placement semantics without imposing an at-most-once continuation rule or allocating an ordered queue.

Each lifecycle-coordinated terminal invocation follows:

1. Enter `OwnershipTopologyGate` before reading ownership state or selecting an action.
2. Pin the exact context snapshot, compiled chain, and interceptor array.
3. Execute the interceptor prefix once. When the exact coordinator node is entered, push one empty coordinator-invocation accumulator and Tracking frame with one Core-issued invocation identity. Interceptors may transform `NewValue` and call continuations zero, one, or several times.
4. At each terminal, build `SubjectOwnershipWriteContext<TProperty>` from that attempt's final transformed value and current segment identity. The lifecycle coordinator performs the incremental initiating-property diff against the persistent committed baseline or that segment's committed-pending overlay, traverses only newly reached route-free subjects in canonical depth-first order, runs an affected-component scan only when selected incoming removal can release ownership, and pins arrays only for the resulting affected subjects.
5. If nested work cancels the current preparation, observe `IsPreparationCancelled`, clear only that tentative revision, settle any prior committed-pending overlay before the nested action, and repeat terminal discovery from final values afterward. Do not pop the invocation frame or replay the prefix. A later terminal after the barrier receives a new segment identity.
6. Validate exact domain/coordinator identity, subject ownership generations, route identities/descriptors, and every affected committed structural-baseline dependency. Permanent incompatibility cancels and throws before the backing writer. The executor's general `Revision` and the caller-captured `currentValue` are not validation inputs.
7. Enter the initiating executor monitor and call the synchronous direct-store writer once. Set `IsWritten`, finalize the existing origin/write state, increment the existing executor `Revision` exactly as the legacy write terminal does, and copy that post-commit label into the ordinary write context for Tracking/connectors. Do not perform an ownership revision recheck or restart because scalar churn changed that label.
8. While retaining the topology gate, publish that attempt's preallocated incremental Core incoming-ledger entries under one affected executor monitor at a time, advance its checked ownership generation, and replace the current segment's property overlay and committed-pending delta. Clear superseded attempt-only reservations without publishing callbacks or routes.
9. Immediately before a supported nested topology operation selects an action, or when downstream returns or unwinds, settle the nearest committed-pending segment. Expose only that segment's final coalesced operation. Tracking records its final baseline first, reconciles callbacks once with pinned arrays, and invokes `TryPublishCommittedRoute` at the exact coordinator boundary. A reentrant committed operation during reconciliation classifies linked pending obligations before it returns: valid older phases remain pending, while an invalidated phase stops only after exact later adoption and replacement. No nested topology means one downstream segment; each nested topology boundary may create one additional segment in the same invocation.
10. After all segments are settled or cancelled, Core invokes `ReleaseSubjectOwnership` once for the coordinator invocation and clears identities, exact segment-start descriptors, overlays, obligation tokens/adoption links, TLS, and pooled storage in `finally`.

The topology gate prevents any concurrent compliant structural/context mutation between validation and commit except synchronous legal reentrancy on the same thread. A legal reentrant structural mutation cancels or settles the affected tentative work through the existing invocation/segment protocol and makes later planning rebase from its committed baseline. Scalar writers remain outside the topology gate and may increment the same executor's legacy `Revision` during preparation, but they cannot alter a correctly classified structural property's storage or committed structural baseline and therefore cause no ownership restart, ABA, or route allocation. Core prevalidates semantic compatibility and reserves mutable operation/reverse capacity before the backing writer. It does not prebuild an immutable route or routed state. After commit, the exact coordinator publication phase performs a final obligation/descriptor check, then creates the route from the then-current immutable executor state. An ordinary stale or losing topology attempt therefore allocates no route object, and a committed owed publication is suppressed only after exact later adoption. PR #474 reverse snapshots, route/service-cache construction, prospective service-walk arrays, and invalidation generations remain measured route-change costs rather than hidden warmed-stable costs.

### Ownership discovery reader contract

`SubjectPropertyMetadata` adds the distinct optional delegate:

Both public constructors add `Func<IInterceptorSubject, string, Type, object?>? getOwnershipValue = null` as their final parameter. Canonical lifecycle traversal invokes it with the exact metadata name and declared type and never invokes ordinary `GetValue`. Proxy lifetime owns subject, `Data`, interceptor, and storage as one collectible component.

An ownership reader may not run read interceptors, derive its result from scalar/external mutable state, invoke context/ownership/topology/metadata APIs, or wait for another thread. Nonintercepted/computed structural properties that cannot meet the direct-storage contract are not valid automatic ownership edges. This mechanically prevents an unversioned scalar/external dependency from becoming a silently stale ownership claim. Generator snapshots, Core Public API, Dynamic, manual metadata, XML, and normal-path source tests explicitly cover the new delegate and compatibility loss.

Direct collection mutation outside an intercepted setter remains outside prospective admission. Supported collection wrappers must turn changes into structural writes. Unobserved external raw mutation has no transactional ownership guarantee.

## Explicit Attach and Detach

The strict APIs are:

```csharp
public static void AttachToContext(
    this IInterceptorSubject subject,
    IInterceptorSubjectContext context);

public static void DetachFromContext(
    this IInterceptorSubject subject,
    IInterceptorSubjectContext context);

public static bool TryGetAttachContext(
    this IInterceptorSubject subject,
    out IInterceptorSubjectContext? context);
```

`TryGetAttachContext` is an ownership query, not lock-free service resolution. It enters the topology gate and settles any nearest ancestor in `CommittedPending` before reading the anchor. If called from a documented callback while the subject is already `Reconciling`, it reads the exact committed anchor through the active overlay/ledger and returns that context or `false` without attempting to resettle the current segment. Its answer is about explicit-anchor commitment only; it does not promise that the public immutable route already agrees during a callback phase whose table intentionally retains the old route. Outside such a phase, normal finalization restores ledger/route agreement before the topology turn is released.

Attach validates null and exact supported plain-context shape before resolving subject services, enters the topology gate, settles any nearest committed-pending ancestor segment, prepares activation, and reserves the explicit anchor. When the one supported official lifecycle coordinator identity is present with its reference-identical handler slot and the root is route-free, Tracking discovers and reserves only that newly reached direct-readable component in canonical depth-first order before Core commits, stopping at already-owned compatible joins. A duplicate anchor, incompatible domain/coordinator, distinct second coordinator reference, or missing exact handler slot throws before callbacks or state change. On true first explicit-root attach, Core commits the anchor/ledger, immediately publishes the configured-context route, and only then begins root lifecycle phase 1; every root lifecycle callback resolves the new route. A coordinator-free domain commits only the root anchor and direct route and then returns: Core does not discover, adopt, release, or route prepopulated or later property descendants, and no recursive lifecycle callback runs. Adding an explicit anchor to an already inherited subject in the same domain is a callback-silent source transfer governed by the route-only matrix rather than the true-root-first-attach boundary.

Detach validates the exact current anchor under the topology gate after settling any nearest committed-pending ancestor segment. Missing or wrong context fails persistently. Core removes only the anchor, chooses a surviving inherited route or reserves final component release, commits, and reconciles. Explicit-to-inherited transfer is callback-silent and governed by the route-only matrix. On true explicit-root final release, descendants complete first, the old root route remains published through every root detach phase 1 through 6, and Core clears it only after the complete root callback sequence. Several roots in one exact configured context share activation/coordinator identity while retaining independent anchors.

Generated and Dynamic constructors taking a context call `AttachToContext` and are strict explicit roots. Parameterless subjects remain route-free until a committed parent edge in a lifecycle-coordinated domain adopts them. A context-constructed child remains explicitly owned when a parent edge disappears.

## Dynamic `AddProperties` and Registry Handshake

`IInterceptorSubject.AddProperties` remains callable before, during, and after activation. Generated and Dynamic implementations delegate to the existing public advanced package-infrastructure interface `IInterceptorExecutor`. The method is public because generated subjects compile in consumer assemblies, but it is not an application-level mutation handle: the writer must synchronously publish the supplied complete dictionary into the same subject and must not retain either argument.

```csharp
public void AddProperties(
    IEnumerable<SubjectPropertyMetadata> properties,
    Action<IInterceptorSubject, IReadOnlyDictionary<string, SubjectPropertyMetadata>> writeProperties);
```

Generated and Dynamic code pass a noncapturing static no-throw writer that casts the supplied subject and publishes its exact immutable private metadata lookup with `Volatile.Write`; their public direct lookup/`Properties` accessor reads that field with `Volatile.Read`. Initial generated and Dynamic metadata publication uses the same memory rule. Core materializes the input once, builds the prospective immutable lookup and prospective committed-order snapshot from that same materialization, and invokes the writer once only after admission succeeds while holding `OwnershipTopologyGate` and the executor monitor. After that writer returns, Core publishes the matching ordered snapshot and any ownership ledger delta in the same guarded commit. Topology-gate exit is the joint ownership linearization point for the committed lookup/order/ledger state.

Lock-free direct metadata lookup readers never read or derive order from the Core ordered snapshot. They may observe either the complete old immutable lookup or the complete new immutable lookup through the volatile field, never a partially mutated dictionary. A topology operation cannot pass the gate until both the lookup write and matching Core order/ledger publication are complete. All semantic validation, ownership-reader calls, and capacity reservation occur before the no-throw writer. Core publishes no ordered snapshot, ledger, Registry wrapper, or generation before that writer succeeds. A custom writer that mutates and then throws violates the existing direct-writer contract; Core still publishes no partial order/ledger/Registry state and does not promise rollback of that application-owned lookup mutation.

The executor treats one public call as one atomic batch. Its first action on method entry is to claim the exact matching thread-local `SubjectMetadataCommitRegistration` token into a local operation slot, before argument enumeration, topology-gate waiting, metadata lookup, or any other application code. From that point a nested call cannot observe or claim the token. One `finally` either invokes it at the exact commit point or discards it on every precommit exit. The remaining sequence is:

1. Enter the topology gate, settle any nearest ancestor committed-pending segment, ensure the executor's initial committed metadata order has been captured once, then enumerate the input exactly once into the existing materialized array. Reentrant public operations triggered by the enumerable run inline. After enumeration, rebuild the outer prospective dictionary against the then-current committed dictionary and build the prospective order by appending the materialized input to the then-current committed snapshot. Preserve current duplicate-name behavior.
2. Classify every new metadata entry through Task 1's retained flag. Only when the subject is already owned in a lifecycle-coordinated domain, invoke each structural entry's `GetOwnershipValue` exactly once into a parallel cold-path value slot. A route-free or coordinator-free subject invokes no ownership reader. Ordinary `GetValue` is never invoked for ownership.
3. If enumeration, duplicate validation, any invoked ownership reader, capacity reservation, or permanent ownership admission fails, invoke no writer and publish neither any metadata entry nor any ownership/projection change. Earlier values in the batch remain private and are cleared.
4. Create one `SubjectMetadataAdditionBatchContext` over all materialized additions and values. When the subject is already owned in a domain with an exact lifecycle coordinator, call `PrepareSubjectMetadataAdditionBatch` once for the complete batch, using one Tracking frame to validate all direct-readable structural additions together and pin the property lifecycle phase for every new entry. A route-free subject or a subject owned in a coordinator-free domain performs no lifecycle preparation or ownership discovery.
5. For an already lifecycle-owned subject, under the executor monitor invoke the no-throw metadata writer once with the complete prospective immutable lookup, then publish the exact prospective committed-order snapshot, all direct-readable structural memberships, and exactly one advanced subject generation in the same topology commit. Invoke the exact claimed metadata commit notification immediately after that commit. Whether notification returns or throws, reconcile once, including property lifecycle attachment for every newly published property in committed input order through its pinned service `IPropertyLifecycleHandler`s then subject property handler, complete route/Registry/parent/baseline and descriptor finalization, and release once in `finally`. For a route-free or coordinator-free subject, invoke the writer once and publish the complete immutable lookup plus the same ordered snapshot without membership, generation, property lifecycle, prepare, reconcile, or provider release work. In both cases topology-gate exit jointly linearizes the lookup and order for later ownership operations.

Every entry in a successful batch on an already lifecycle-owned subject participates in the one generation and property lifecycle transaction. Only structural metadata with `GetOwnershipValue` performs ownership discovery and membership work. Scalar/nonstructural metadata and structural metadata without the reader still publish and receive property lifecycle attachment but contribute no current edge; a future gated structural setter final value is tracked. A route-free or coordinator-free publication receives none of that lifecycle or ownership work, and a later true lifecycle attach initializes every then-current property in `SubjectOwnershipView` order and discovers every then-current direct-readable structural edge in normal attach order. Two structural entries, a scalar plus structural entry, a scalar-only batch, structural metadata without a reader, and a failure in the second ownership reader all therefore use one all-or-nothing metadata and order publication point. A mixed lifecycle-owned batch has exactly one prepare, commit, reconciliation, and release. Cold metadata current values may box value-type structural candidates. Derived `base(context)` followed by generated `AddProperties` and Dynamic batch additions use this same transaction and append order.

Registry's `RegisteredSubject.AddProperty` uses exact commit identity rather than name or value inference:

1. Allocate the exact `RegisteredSubjectProperty` and its linked commit node, then call `SubjectMetadataCommitRegistration.Register(Subject, commitCallback)`. The token is bound by reference to this wrapper. Public `Properties`, `TryGetProperty`, and snapshots do not consult it.
2. Call `Subject.AddProperties`. The first instruction in the Core executor entry claims that exact token into this operation before input enumeration or any application callback. An unregistered nested same-subject `AddProperties` from outer enumeration cannot steal it. At the single Core metadata/ledger commit, before any lifecycle/property/user callback, Core invokes the token once and Registry links that exact wrapper into its committed list and invalidates its frozen snapshot under the topology turn. The official notification performs that exact promotion before any exceptional test injection and has a no-throw production contract.
3. A precommit rejection disposes the uninvoked token and wrapper. Neither metadata nor Registry property is public.
4. A commit-notification or later lifecycle/property callback exception leaves the exact immutable metadata lookup, ordered snapshot, ledger delta, generation, and wrapper committed. Core captures the notification EDI at its exact precedence slot, never invokes the token again, and continues full Tracking reconciliation plus route/Registry/parent/baseline/descriptor finalization and provider release in `finally`. An earlier downstream/writer/permanent-incompatibility exception remains primary; otherwise notification exception wins over later callback/finalization exceptions and is rethrown with its stack only after consistency work completes. There is no rollback, input replay, wrapper inference, or partial Core order/Registry state.

Nested same-thread equal or same-name metadata operations carry distinct tokens. A nested commit can promote only its own wrapper. If it makes an outer operation duplicate or cancels the outer tentative batch, the outer rejects or restarts without promoting its token. No metadata equality, name lookup, or public dictionary observation infers commit. Implementation migration removes the old manual null-to-value intercepted write, separate `AttachSubjectProperty` workaround, and lifecycle-only pending lookup; none is retained as a lifecycle contract. This is a cold path and adds no property hot-path branch.

## Exact Callback Order and Route Visibility

Tracking pins every array required by a segment before Core marks that segment committed. Ordinary one-context order is preserved within every settlement. The reference-identical official `ILifecycleInterceptor`/`ILifecycleHandler` element defines one logical coordinator phase at its exact index in the immutable handler array. `WithLifecycle()` supplies the built-in `LifecycleInterceptor`, whose advanced phase replaces its ordinary handler callback at the former `ContextInheritanceHandler` recursion boundary. There is no separate coordinator-rank calculation or supported coordinator that lacks the exact handler slot.

Lifecycle callbacks have a no-throw application contract. The built-in Tracking coordinator nevertheless owns one exact pinned ordered callback cursor for every affected reconciliation and dispatches each lifecycle service handler, subject handler, event subscriber, and property handler as an individual obligation. For final release this is the same entry-mode iterative forest cursor defined above, not a second callback list or traversal. The built-in `LifecycleInterceptor` event accessors maintain a CAS-published immutable subscriber-entry array. Add uses a compare/exchange loop to append one entry, preserving duplicate subscriptions and exact registration order. Remove uses a compare/exchange loop to remove the last delegate-equal matching entry, matching standard event behavior, and is a no-op when no match exists. Concurrent add/remove operations are linearizable at their successful CAS. Reconciliation pins the exact immutable array reference once per affected event phase and indexes it directly; later add/remove, including mutation from a callback, affects only future operations. Dispatch never calls `Delegate.GetInvocationList`, copies an invocation list, or allocates on the no-throw warmed path. The existing immutable service/property arrays and inline-first pooled affected entries supply the rest of the cursor without copying or allocating.

Immediately before each callback call, Tracking marks that exact obligation `Delivered`, meaning attempted once even if it throws. Exception-safe dispatch catches only actual callback exceptions, captures the first one with `ExceptionDispatchInfo` on the exceptional path, records later callback exceptions diagnostically without replacing it, and continues every still-owed callback or exact later adopted replacement in ordinary order. A throw before the coordinator does not skip callbacks after it or entry-mode-specific route work: a property-carried publication or clear still occurs at the coordinator, an explicit-root attach route is already published, and an explicit-root detach clear still occurs after phase 6. A throw after the coordinator does not skip subject, event, property, descendant, independent-sibling, or explicit-root post-phase-6 clear obligations still due. Tracking completes its baseline, parent projection, callback, and property-carried constrained route-publication cursor before it throws the first captured EDI; Core completes any explicit-root boundary publication/clear obligation before that EDI escapes the overall reconcile/finalize boundary. Core does not resume or reenter a partially escaped Tracking cursor: it observes only a completed reconciliation return or a completed-reconciliation exception, preserves already committed Registry and ledger state, completes descriptor finalization, and calls final release in `finally` under the established precedence.

Cancellation, restart, stale generation or route identity, contention, and obligation adoption remain control flow governed by their wait/restart/no-op rules and never manufacture a callback or reconciliation exception. Exception handling may be isolated in a cold helper so scalar, read, invoke, service-resolution, and no-callback stable paths gain no exception-state branch or managed allocation; the normal no-throw lifecycle dispatch path captures no EDI and allocates zero managed bytes.

|---|---|---|---|
| before 1 | iteratively complete every descendant release tree | old configured-context route remains published for the root | release cursor; no root callback yet |
| 1 | each root property in committed `SubjectOwnershipView` order: service `IPropertyLifecycleHandler`s, then subject property handler | old configured-context route and old baseline | current-route property-handler array for the root |
| 2 | root `SubjectDetaching` event subscribers in registration order | old configured-context route and committed detach projection | pinned ordered event-subscriber entries |
| 3 | root's own `ILifecycleHandler` | old configured-context route and committed detach projection | subject instance |
| 4 | root lifecycle service handlers before coordinator, in forward order | old configured-context route | current-route lifecycle array, pre-coordinator segment |
| 5 | exact coordinator phase, with no root route clear and no remaining descendant work | old configured-context route | logical insertion index in same pinned lifecycle array |
| 6 | root lifecycle service handlers after coordinator, in forward order | old configured-context route | same pinned lifecycle array, post-coordinator segment |
| after 6 | Core clears the root route, completes unregister/reverse invalidation, and marks release complete; no callback | route-free state | Core exact explicit-root clear obligation |

Property-carried release uses phases 1 through 4 as its pre-order prefix, performs descendants and route clear at phase 5, and uses phase 6 as its post-order suffix. Explicit-root release completes descendants before root phase 1, keeps the old route visible throughout root phases 1 through 6, and clears it only afterward. Explicit-root and property-carried visibility boundaries are current characterization contracts, not interchangeable implementations.

Ownership-source changes within one already active lifecycle domain do not manufacture subject activation or deactivation. This matrix applies only when the subject remains active; it does not replace the explicit-root first-attach or final-detach boundaries above. Their exact matrix is:

| Transition | Lifecycle callbacks | Route, descriptor, and opaque identity action | Array visibility |
|---|---|---|---|
| inherited subject gains its first compatible explicit anchor | none | commit the anchor; if the effective target changes, publish the fresh explicit route with a different identity and invalidate resolved service/interceptor state plus reverse downstream dependents | no handler array is invoked; branch-only handlers are future operations only |

| nonselected parent membership is added or removed | emit only that actual normal nonfinal addition or removal; `ReferenceCount` is the remaining property-membership count and may be zero when an explicit anchor keeps the subject live, while `IsContextDetach` remains false; do not transfer the route | descriptor, route, and identity remain exact | ordinary prospective array for addition or current array for removal |

No inherited-to-explicit, explicit-to-inherited, or selected-parent transfer emits `SubjectAttached`, `SubjectDetaching`, property attach/detach phases, or a synthetic lifecycle addition for the newly selected route. An actual distinct membership addition in the same atomic delta still receives its ordinary addition later because all removals precede additions; route selection itself adds no callback. When the internal exact descriptor survives, its opaque identity survives. When the descriptor changes, route publication issues a different opaque identity even if the effective target and domain compare equal, and completes PR #474 reverse invalidation before the topology turn can admit another structural operation. Any stateful ownership authority that exists only on a newly selected branch must already be a shared live instance or initialize lazily on first future use; this silent transfer does not provide an activation callback for branch-local state.

If such a transfer occurs reentrantly while an ancestor reconciliation tail still has pending phases, the later transfer classifies those exact obligations before it returns. A transfer that preserves the exact route identity preserves the dependencies, so semantically valid ancestor and descendant phases remain owed by their older pinned arrays. A transfer that changes identity adopts only the ancestor publication and descendant phases whose captured selected-parent subject route identity became invalid, and its later frame owns their correct serial replacements. Unrelated sibling phases remain in the older tail. The transfer's own actual nonfinal membership removal is delivered once by the later operation and does not synthetically satisfy or erase a different pending obligation.

Nonfinal parent addition/removal otherwise invokes the current lifecycle handler change in the same service/subject ordering but does not repeat first-attach event/property phases. Structural replacement remains detach old membership before attach new membership. ## Exact Coordinator Exception Deferral

`WriteInterceptorChain<TProperty>` records the exact lifecycle coordinator node reference/index in the pinned chain. Only that node uses a special continuation and owns one coordinator-invocation accumulator. A route-free composed coordinator without a matching Core operation remains an ordinary transparent interceptor.

The node invokes downstream in `try/catch`. Each successful terminal below it commits one ordered Core ownership generation/delta into the current segment overlay. An ordinary repeat replaces that segment's final delta; a mandatory barrier settles it and a later repeat uses a new segment. If downstream throws after one or more stores, the node captures the first exception with `ExceptionDispatchInfo`, settles the final committed-pending segment, and has Core finalize and release the invocation in `finally`. The original downstream exception is rethrown with its stack. A permanently incompatible later attempt rejects before its writer, settles an earlier pending segment during unwind, and keeps the incompatibility as the primary exception. A direct writer exception before mutation cancels that attempt, settles an earlier committed-pending segment, and remains primary. If no segment has a successful store, no reconciliation runs. If a repeater is upstream, each call reaches a fresh coordinator invocation and follows this sequence independently. The executor's legacy commit-order `Revision` may be carried to existing change records after a successful terminal but is never consulted by this coordinator path.

If a user callback throws during a mandatory barrier, its exact obligation was marked `Delivered` immediately before invocation and is never replayed. The requested nested structural, attachment, metadata, context, or ownership-query operation has not selected an action and has no effect. Tracking captures the first callback exception with EDI, continues its complete pinned reconciliation cursor including all still-owed callbacks and route publications, preserves committed baseline/Registry/parent state, and then throws that first EDI only after its reconciliation work is complete. Core catches that completed-reconciliation exception for precedence, completes ledger/descriptor finalization, and calls `ReleaseSubjectOwnership` in `finally`; it never calls back into Tracking to resume a cursor after `ReconcileSubjectOwnership` escaped. Reentrancy during later callback dispatch uses the `Reconciling` later-generation rules and cannot resettle the same segment. A nested operation that fails before commit leaves ancestor obligations pending; one that commits completes classification and all replacements it adopted before it returns or rethrows. This obligation bookkeeping introduces no new exception kind or precedence.

The same exception path applies when a callback lets the stable same-subject true-inverse `InvalidOperationException` escape. The nested inverse operation has no writer, ledger, route, callback, or projection effect; the currently executing callback remains marked delivered; Tracking finishes the original attach/detach cursor and entry-mode route boundary; then the inverse exception participates as that callback's actual exception under first-EDI precedence. Catching it inside the callback leaves no exception for Tracking and the original cursor continues directly.

Exception precedence is:

1. an earlier downstream, direct-writer, or permanent-incompatibility exception;
2. otherwise an exact metadata commit-notification exception from official infrastructure violating its no-throw obligation;
3. otherwise the first actual lifecycle callback exception in exact dispatch order;
4. otherwise Core finalization exception.

A metadata commit-notification exception occurs after the immutable lookup, ordered snapshot, Core ledger/generation, and exact Registry promotion are committed. Core captures its first EDI at precedence position 2, marks the one-shot token consumed, and does not unwind out of the coordinator boundary yet. It runs the same complete Tracking callback cursor and mandatory route, Registry, parent, baseline, descriptor, and Core finalization work as a successful committed batch, invokes `ReleaseSubjectOwnership` in `finally`, records any later callback/finalization exceptions without replacement, and only then rethrows the notification EDI. No input, token, writer, callback, or publication is replayed and no committed metadata state is rolled back.

Tracking completes required reconciliation internally after a callback error and reports each secondary callback exception through `System.Diagnostics.Trace.TraceError`; Core completes finalization/release after Tracking returns or throws, and no later error replaces an earlier exception in the precedence above. Trace reporting is exceptional-path diagnostic work only. Failure of an installed trace listener is treated as another secondary callback-dispatch diagnostic and cannot replace the first callback exception or stop reconciliation. The built-in Registry commit notification does not throw. If downstream throws before terminal commit, no operation is exposed, Tracking reconciliation does not run, Core cancels/releases the operation, an unclaimed Registry token is discarded, and the original exception propagates. No cancellation, restart, stale-state, contention, or other library control-flow outcome is represented by an exception.

## Compile-Time Internal Ownership Diagnostics

Ownership complexity diagnostics exist only when the dedicated compilation symbol `NAMOTION_INTERCEPTOR_OWNERSHIP_DIAGNOSTICS` is defined. The internal build property `EnableOwnershipDiagnostics=true` appends that symbol in Core, Tracking, and the diagnostics test compilation. It is a test/build instrument, not a public API, package feature, runtime switch, environment variable, or supported application contract. The normal value is absent/false.

In an enabled build, the real Core operation batch/segment frame and real Tracking reconciliation/traversal frame each contain an operation-local value counter struct under `#if NAMOTION_INTERCEPTOR_OWNERSHIP_DIAGNOSTICS`. Counter increments occur inline at the actual traversal, lookup, pin, settlement, publication, and capacity-growth sites, not in a parallel model. The merged counter payload contains exactly `SuppliedOccurrences`, `IdentityLookups`, `NewlyReachedSubjects`, `NewlyReachedEdges`, `ReleaseComponentSubjects`, `ReleaseComponentEdges`, `AffectedSubjects`, `PinnedLifecycleArrays`, `PinnedPropertyArrays`, `SettlementSegments`, `RoutePublications`, `OperationBufferGrowth`, and `PersistentBufferGrowth`. `OperationBufferGrowth` and `PersistentBufferGrowth` count actual capacity-growth events separately; they are not allocation-byte estimates.

Counter semantics are exact. `SuppliedOccurrences` counts every occurrence supplied by structural value enumeration, including duplicates. `IdentityLookups` counts every reference-identity index lookup, hit or miss, across Core and Tracking. Newly reached counters count first traversal of route-free subjects and their membership edges. Release-component counters count subjects and edges examined while constructing `C` and `R`, not callbacks. `AffectedSubjects` counts each unique affected reconciliation entry once. Pinned-array counters count exact lifecycle/property array pin actions, even when two pins reference the same immutable array. `SettlementSegments` increments once when Core settles one committed segment. `RoutePublications` increments only for a successful exact route install, replace, or clear, never for an attempted/stale `false` publication. Buffer-growth counters increment once per actual operation-local/TLS or persistent topology-storage capacity increase respectively.

Every immutable internal diagnostics snapshot has a header containing the exact internal invocation identity and segment identity; those keys are metadata, not additional counters. Each segment keeps its own value counters in the real invocation frame. Repeated segments in one invocation and synchronous reentrant invocations therefore produce distinct snapshots and are never summed by ambient thread, subject, or completion order. Tracking submits its segment counter contributions together from the matching `ReleaseSubjectOwnership`; Core submits its corresponding per-segment contributions and completes publication during final invocation cleanup before clearing the frame. Core's internal synchronized sink merges each pair only by the exact invocation/segment keys and retains one immutable completed snapshot per key for the active capture lease. A coordinator-free Core operation publishes a completed Core-only snapshot with zero Tracking contribution.

The explicit internal capture lease is exclusive and synchronized. `Acquire` installs one active capture under a private diagnostics-only monitor; enabled operations publish only to that lease. The lease alone can call `ReadAndReset`, which returns the immutable completed snapshots and atomically clears the captured set, and `Dispose` performs a final reset and removes the lease. A Tracking-internal test wrapper uses the existing Core-to-Tracking friend access, copies the internal Core records into Tracking-owned internal test records, and exposes them through the existing Tracking-to-tests friend access. No new `InternalsVisibleTo`, public facade member, conditional public API, or cross-assembly callback interface is added. Diagnostics tests use one nonparallel xUnit collection and acquire one lease per test, so unrelated tests cannot race a read/reset or contribute an invocation accidentally.

When the symbol is absent, preprocessing removes the counter structs, frame fields, increments, capture calls, snapshot types, sink, monitor, lease, wrapper, and enabled-capture test bodies. Disabled production traversal contains no diagnostics branch, TLS slot, interface member, allocation, frame-size increase, method call, or increment instruction. ## Memory Ownership and Cleanup

- `OwnershipTopologyGate` is one static object and the only ownership/topology operation monitor.
- Each initialized subject executor owns exactly one private property/state monitor. Removing public `SyncRoot` removes the generated/Dynamic root object; no second subject lock is introduced.
- Each executor owns one exact committed metadata publication snapshot for its subject. Initial generated, Dynamic, or manual enumeration is captured once under the topology turn; a successful `AddProperties` commit replaces it with the old exact prefix plus the once-materialized additions, while rejection or cancellation leaves it unchanged. The snapshot retains only the subject's committed `SubjectPropertyMetadata` references and serves `SubjectOwnershipView` count/index reads directly without an enumerable or copy.
- Inactive/route-free executors retain no allocated ownership graph state beyond the existing executor, private monitor, and scalar Core-owned route-free identity epoch. Ownership graph state is allocated on first prospective anchor/membership and cleared on final release; entering or remaining route-free allocates no descriptor or object.
- First parent membership and first batch entry are inline. Overflow collections are lazy, insertion ordered, pooled where operation-local, and cleared item by item.
- Core's incoming ownership ledger is indexed by subject executor and exact incoming `PropertyReference`; its explicit anchor, selected parent, internal route, opaque route identity, domain, coordinator, and generation are the authoritative ownership truth. Core rents prefix and coordinator batches from a thread-static LIFO pool and never clones the ledger into them.
- Core owns one `finally` for every batch attempt and one final release for every coordinator invocation. It clears pending subject references, segment-start and superseded exact descriptors, invocation/segment/route identities, committed value overlays, committed-but-unpublished action-overlay route inputs/service arrays/chains, obligation states/adoption identities, coordinator/domain references, TLS links, and pool items before return. Publication or exact later-operation adoption clears the corresponding action-overlay entry as soon as it stops being selectable. No action-overlay reference survives finalization or enters executor/context immutable state. The executor retains only its current scalar route identity epoch after operation cleanup.
- Tracking owns one thread-static pooled LIFO reconciliation frame per nested coordinator invocation, not per segment. Affected action entries carry obligation state and exact generation/opaque subject and selected-parent route-identity dependencies inline; synchronous nested frames link only while classifying adoption. The same frame owns the one iterative release cursor, selected-final-carrier forest links, `ReleasePlanned`/`ReleaseEntered`/`ReleaseCompleted` marks, entry modes, and metadata/occurrence indexes without a second pre/post traversal list. `ReleaseSubjectOwnership` is called exactly once by Core after all of that invocation's segments and clears invocation/segment/route identities, including every private descriptor reference physically contained by an opaque routed identity, plus handler arrays, cursor/forest links and marks, segment-start and pending baselines, occurrences, subjects, properties, obligation tokens/adoption links, and previous-frame links. Tracking retains no separately exposed or semantically inspectable route descriptor.
- Tracking's callback-exception slot remains null on the no-throw path. It retains only the first exceptional-path `ExceptionDispatchInfo` until the completed reconciliation throws it, and final release clears any remaining reference. Secondary callback exceptions are recorded diagnostically without prescribing a carrier here and without persistent per-subject storage.
- Immutable interceptor/service and lifecycle-event subscriber arrays are retained only by immutable published state or the current stack. Pinned array structs do not copy underlying arrays. Event add/remove publishes a replacement immutable subscriber array by CAS; reconciliation releases its pinned old reference with the frame.
- Registry commit tokens/wrappers live only until precommit discard or exact commit-time linked publication. A postcommit notification exception does not discard or replay the token; the exact promoted wrapper remains committed while final release clears transient Registry/parent projection state through ordinary reconciliation.
- A lifecycle-owned metadata batch retains its once-materialized entries, prospective order storage, ownership-value slots, and pinned property-handler array references only in the one transaction frame through release; precommit failure clears them all. Generated and Dynamic subjects publish the complete immutable lookup through `Volatile.Write`, and direct readers use `Volatile.Read`; Core publishes the matching ordered snapshot under the same executor-monitor/topology turn. Topology-gate exit jointly linearizes lookup/order/ledger for ownership, while lock-free lookup readers see complete old or new lookup and never retain the ordered snapshot. Route-free and coordinator-free metadata publication creates no provider frame beyond the cold Core materialization needed for the immutable lookup and ordered snapshot.
- Tracking's persistent outgoing baseline is indexed by subject and structural property, with a compact committed unique-child array, stable ordinals between settlements, and lazy reference-identity lookup. It contains only committed structural values and first-occurrence projection metadata. It is not an ownership source and removes entries on final release.
- A nontrivial Tracking property diff lazily uses exactly two property-owned dense scratch banks indexed by committed child ordinal. Bank 0 is sufficient until a later tentative revision must coexist with a committed-pending overlay; bank 1 is allocated only for that case. Overlay-only children remain in frame-local inline-first provisional entries. Cancellation and supersession clear the tentative role, successful commit swaps roles, and settlement consumes and clears both banks before callbacks or nested topology. No bank content is committed truth.
- Dense-bank semantic visit tokens are scratch state, never ownership generations, route identities, invocation identities, or segment identities. A visit token that cannot advance without wrapping performs one complete synchronous sweep over both banks, clears every cell and all associated object/key references, and only then resets to its initial nonzero scratch value. No bank may be leased and no callback or nested topology action may interleave with that sweep. Permanent identity counters never use this reset path.
- A failed or cancelled tentative attempt publishes none of its proposed anchor, membership, route, baseline, Registry wrapper, or activation lifetime edge. It does not roll back an earlier committed-pending segment overlay, which settles normally before nested work or unwind.
- In an enabled diagnostics build, counter fields live only in the corresponding operation/reconciliation frame and completed immutable snapshots live only in the active capture lease. `ReadAndReset` and `Dispose` clear the captured set; final frame cleanup clears all in-progress contributions. Reentrant invocation and segment records share no mutable counter storage. A disabled production build retains none of these fields, records, references, or synchronization objects.

Weak-reference tests cover failed first attach, cancelled tentative discovery, detached explicit root, released cycle, multi-parent final detach, selected-final-carrier forests and cursor entries after completion/exception/adoption, synthetic metadata rejection, superseded/adopted owed phases and their linked nested frames, segment-start descriptor replacement and scalar identity cleanup, committed-but-unpublished overlay contributing-state identities and route/service/chain inputs after context-publication invalidation, publication, adoption, or finalization, both dense scratch banks after cancellation/supersession/settlement/shrink/property removal/final release, and provider-frame cleanup after each exception precedence row.

Every new thread-static `List`, `HashSet`, `Dictionary`, or release-cursor operation pool follows PR #474's `MaximumRetainedTraversalSize = 1024` policy. Release clears all references. If any retained operation-list/cursor capacity or operation set/dictionary count/capacity-equivalent exceeds 1024, that oversized storage is dropped rather than returned to the thread-static holder. Property-owned dense scratch banks are not operation-pool storage: capacity above 1024 is retained only while that property's committed topology remains large and stable, and is cleared and dropped or resized when topology shrinks, the property is removed, or the subject is finally released. ## Capability Losses

- Public fallback mutation no longer attaches, detaches, or establishes inheritance.
- A subject cannot have several explicit anchors or unrelated ownership domains.
- An owned factory child cannot be stolen or silently retained as a different root.
- Recursive property ownership is unavailable without the exact supported official Tracking lifecycle coordinator and its reference-identical `ILifecycleHandler` slot. `WithLifecycle()` is the standard built-in registration. A plain coordinator-free context owns only explicit roots and composes services.
- Shallow lifecycle without recursive property inheritance is removed.
- An active initiating structural chain cannot synchronously attach or detach its own subject; a route-free structural chain cannot synchronously change its own coordinator. Scalar prefixes retain current self-attach/detach behavior.
- While one subject's exact lifecycle callback obligation is executing, nested attach/detach or structural work cannot cause the true inverse ownership transition of that same subject. It fails persistently for that callback context before nested effects. Other-subject topology work and same-subject noninverse work remain supported.
- The public `IInterceptorSubject.SyncRoot` member and public atomic-lock snapshot capability are removed. Generated, Dynamic, and manual subject shapes must rebuild.
- Callbacks, factories, ownership readers, structural traversal, and custom writers cannot synchronously wait for another thread needing the topology turn.
- Lifecycle callbacks are a no-throw application contract. If one nevertheless throws, that callback is treated as attempted/delivered, every remaining owed lifecycle callback and mandatory consistency action still completes, and the first actual callback exception is rethrown only after reconciliation and Core finalization/release.
- Computed/nonintercepted/scalar-dependent/external-state getters are not automatic ownership edges. Automatic discovery requires the distinct direct storage reader.
- Structural storage may change only through the canonical gated structural setter or `AddProperties` path. Calling the scalar overload for a structurally classified property, mutating its backing storage directly, or supplying a custom bypass forfeits ownership consistency, ABA, and deadlock guarantees.
- A branch-only stateful ownership authority cannot depend on a synthetic activation callback when an already active subject silently transfers ownership source within the same lifecycle domain. It must be a shared live instance or initialize lazily on future use.
- Official lifecycle infrastructure must treat Core-issued invocation/segment and route identities as synchronous opaque capabilities: it cannot construct a valid identity, retain one after final release, infer a target/descriptor, or continue preparation after `IsPreparationCancelled` becomes true. Third-party implementation of the advanced public infrastructure seam is discouraged and unsupported; changes remain tracked public API and follow normal package breaking-change/version policy.
- Permanently non-stabilizing direct ownership readers and sustained adversarial monitor contention are unsupported liveness conditions.
- Disconnected domains lose parallel structural and configuration throughput.

Preserved capabilities include nonunique service mutation, identity-preserving composition fallback add/remove, same-thread cross-context `TryAddService` reentrancy, branch-local services, cycles, DAGs, repeated references, compatible multiple parents, arbitrary supplied collection and dictionary implementations, `AddProperties` at any time, strict explicit roots, composition-only fallbacks, and ordinary one-context callback behavior.
